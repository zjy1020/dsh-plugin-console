# 第 07 章 打包与交付

> 本章讲：`src/` 里的代码怎么变成一个能在别人机器上双击运行的 Windows 程序，以及这条路上每个坑的真实证据在哪。
> 每条结论后跟 `路径:行号`。凡是本轮没有独立复测、只存在于交接记录里的数字，都标「交接记录」，并在 7.6 汇总。

## 7.0 证据口径

| 等级 | 含义 | 标记 |
|---|---|---|
| **实测复现** | 本轮亲手跑命令算出的数，命令随文附上 | 数值后标 `（本轮实测）` |
| **源码直读** | 读某一行读出的事实 | 直接给 `路径:行号` |
| **交接记录** | 前序工作留下的结论/截图，本轮未复测（多为需起 GUI 才拿得到的 Windows 侧数据） | 标 `（交接记录）` |

复现手段（都在项目根执行，只读、不改产物）：ICO 帧表直接解析目录项；PNG 尺寸读 IHDR（offset 16 起大端 4 字节）；内嵌图标用 `[System.Drawing.Icon]::ExtractAssociatedIcon(<exe>)`；白底统计用 Python 3.14.2 + PIL 12.0.0 + numpy 复算 `scripts/make-icons.py` 的 floodfill。

## 7.1 构建与打包配置

### 7.1.1 `package.json`

| 字段 | 值 | 位置 |
|---|---|---|
| `name` | `dsh-plugin-console` | `package.json:2` |
| `productName` | `DSH 插件台` | `package.json:3` |
| `version` | `0.1.0` | `package.json:4` |
| `private` | `true` | `package.json:5` |
| `main` | `./out/main/index.js` | `package.json:8` |
| `author` | `YG` | `package.json:7` |

`main` 指向 electron-vite 的默认输出位置（`package.json:8`），`dev` 与 `build` 往同一个 `out/` 写（`package.json:10-11`），所以开发与打包走同一份入口路径。

**为什么刻意不加 `"type": "module"`** —— 全文 30 行无 `type` 字段（`package.json:1-30`），三条互相咬合的证据：

1. 主进程源码依赖 CJS 的 `__dirname`：`src/main/window.ts:57` 的 `preload: join(__dirname, '../preload/index.js')`、`src/main/window.ts:127` 的 `win.loadFile(join(__dirname, '../renderer/index.html'))`。ESM 里没有 `__dirname`，加了会在运行期 `ReferenceError`，不是编译期报错。
2. 主进程产物确实是 CJS：本轮实测 `out/main/index.js` 里 `require(` 出现 **11 次**、行首 `import` **0 次**；文件头是 `// \0rolldown/runtime.js` 包装（`out/main/index.js:1`）。
3. preload 产物也是 CJS：`out/preload/index.js:1` 就是 `let electron = require("electron");`（本轮实测）。Electron 的 preload 在 `sandbox: false`（`src/main/window.ts:58`）下虽支持 ESM，但必须 `.mjs` + 显式 `type: module`；混用会静默失败 —— 渲染层 `window.dsh` 变 `undefined`，界面全空而主进程不报错。这是 ESM preload 最经典的坑。

**scripts 六条**（`package.json:9-16`）：

| 脚本 | 命令 | 位置 |
|---|---|---|
| `dev` | `electron-vite dev` | `package.json:10` |
| `build` | `electron-vite build` | `package.json:11` |
| `preview` | `electron-vite preview` | `package.json:12` |
| `typecheck` | `tsc --noEmit -p tsconfig.node.json && tsc --noEmit -p tsconfig.web.json` | `package.json:13` |
| `dist` | `electron-vite build && electron-builder --win --x64 --config electron-builder.yml` | `package.json:14` |
| `dist:dir` | `electron-vite build && electron-builder --win --x64 --dir --config electron-builder.yml` | `package.json:15` |

两条打包脚都 `&&` 先 build 再打，不会拿旧 `out/` 打新包。`dev` 下 `ELECTRON_RENDERER_URL` 由 electron-vite 注入，`src/main/window.ts:8` 读它决定 `loadURL` 还是 `loadFile`。

**devDependencies 全部 11 项**（`package.json:17-29`），声明为 `^`，实装版本本轮从 `node_modules/<pkg>/package.json` 读：

逐项（格式为 `包` 声明→实装 `行号`）：`@types/node` `^24.7.0`→24.19.2（`:18`）、`@types/react` `^19.2.0`→19.3.0（`:19`）、`@types/react-dom` `^19.2.0`→19.3.0（`:20`）、`@vitejs/plugin-react` `^6.1.2`→6.1.2（`:21`）、`electron` `^45.2.1`→45.2.1（`:22`）、`electron-builder` `^26.18.0`→26.18.0（`:23`）、`electron-vite` `^6.0.0`→6.0.0（`:24`）、`react` `^19.3.1`→19.3.1（`:25`）、`react-dom` `^19.3.1`→19.3.1（`:26`）、`typescript` `^5.9.3`→5.9.3（`:27`）、`vite` `^8.3.5`→8.3.5（`:28`）。

**没有 `dependencies` 段**，这在打包语境下是关键：`npmRebuild: false`（`electron-builder.yml:24`）+ `files` 只收 `out/**/*` 与 `package.json`（`electron-builder.yml:9-11`），意味着**不往 asar 里塞任何 `node_modules`**。主进程能用的第三方包只有 Electron 内建的（`electron` 本体被 `externalizeDepsPlugin()` 外置）。任何时候新增运行期依赖，打包后都会 `Cannot find module` —— 见 7.5.4 风险②。

### 7.1.2 `electron.vite.config.ts`

全文 17 行，三个目标：`main` 用 `externalizeDepsPlugin()`（`electron.vite.config.ts:5-7`）、`preload` 同（`:8-10`）、`renderer` 用 `react()` + `chunkSizeWarningLimit: 2000`（`:11-16`）。

**为什么刻意不写自定义 `input` / `root` / `alias`**：

- electron-vite 的默认约定是 `src/main/index.ts`、`src/preload/index.ts`、`src/renderer/index.html`，这三个文件都真实存在（`src/renderer/index.html:32` 里 `<script type="module" src="/src/main.tsx">` 也与默认 `root` 咬合）。写自定义 `input` 只是把约定抄一遍，抄错一处就构建不出东西。
- 一处 `alias` 都没用：跨进程共享类型走相对路径（`src/main/tray.ts:19-20`、`src/renderer/src/components/TitleBar.tsx:10`）。没别名就省掉了「tsconfig 的 `paths` 要和 vite 的 `alias` 手抄一致」这个双份维护点 —— 两个 tsconfig 里也确实没有 `paths`（见 7.1.3）。
- `externalizeDepsPlugin()`（`:6`、`:9`）把依赖留给运行期 `require`，保证 `electron` 本身不被内联；本工程无 `dependencies`，它实际是「哪天加了依赖别被打进去」的保险。
- `chunkSizeWarningLimit: 2000`（`:14`）为压掉单 chunk 超 500 kB 的告警：本轮实测 `out/renderer/assets/index-DqJgJxfm.js` = 872,216 B，确实超默认阈值。

### 7.1.3 三个 tsconfig 的分工

`tsconfig.json` 是空壳 + 引用表：`files: []`（`tsconfig.json:2`）让根项目自己不含文件，只负责把两个子项目串起来（`tsconfig.json:3`）；否则编辑器会拿一个什么都不 include 的根配置去套任意文件。

| | `tsconfig.node.json` | `tsconfig.web.json` |
|---|---|---|
| `target` / `module` / `moduleResolution` | `ES2022` / `ESNext` / `bundler`（`:3-5`） | 同左（`:3-5`） |
| `lib` | `["ES2023"]`（`:6`） | `["ES2023","DOM","DOM.Iterable"]`（`:6`） |
| `jsx` | 无 | `react-jsx`（`:7`） |
| `types` | `["node"]`（`:7`） | 无 |
| `noEmit` / `composite` | `true` / `true`（`:9-10`） | `true` / `true`（`:9-10`） |
| `include` | `src/main/**/*.ts`、`src/preload/**/*.ts`、`src/shared/**/*.ts`、`electron.vite.config.ts`（`:20`） | `src/renderer/**/*.ts`、`src/renderer/**/*.tsx`、`src/shared/**/*.ts`、`src/preload/*.d.ts`（`:20`） |

三个设计点：

1. **`src/shared/` 两边同时 include**（`tsconfig.node.json:20` / `tsconfig.web.json:20`）。`src/shared/ipc.ts`、`src/shared/types.ts` 是「唯一真相」，必须两边可见且同一套 `target/lib` 解析，才不会出现契约漂移。
2. **web 侧只收 `src/preload/*.d.ts`，排除 `src/preload/index.ts`**（`tsconfig.web.json:20`）。`src/preload/index.d.ts` 仅 130 B，只用来声明 `window.dsh` 形状；排掉实现文件后，渲染层就没法顺着 import 摸到 `ipcRenderer` 类型，也就没人会手滑在界面里直接调 node API。
3. **node 侧把 `electron.vite.config.ts` 收进来**（`tsconfig.node.json:20`）：配置文件跑在 Node 里、用 `defineConfig`，归属 node project 才不会在 `import react from '@vitejs/plugin-react'`（`electron.vite.config.ts:2`）上撞类型错。

两个 project 都 `noEmit: true`（`:9`）—— 类型检查归 `pnpm typecheck`（`package.json:13`），真正产出 JS 的是 rolldown 不是 tsc。`composite: true`（`:10`）为 `references` 服务，副作用是根目录留下 `tsconfig.node.tsbuildinfo`（56,050 B）与 `tsconfig.web.tsbuildinfo`（46,922 B）（本轮实测），而 `.gitignore:1-6` 没忽略它们 —— 可直接删的无害残留。

### 7.1.4 `electron-builder.yml`

**基本信息**：`appId: com.yg.dsh-plugin-console`（`:1`）、`productName: DSH 插件台`（`:2`）、`copyright`（`:3`）。`appId` 与主进程 AUMID 是**同一个字符串**（`:1` ↔ `src/main/index.ts:14`），这是 7.3.6 任务栏合并现象的根源。

**directories**（`:5-7`）：`output: release`（`:6`）、`buildResources: build`（`:7`）。`build/` 只是构建资源目录，**不会**被打进包 —— `release/builder-debug.yml` 的 `firstOrDefaultFilePatterns` 第一条就是 `'!build{,/**/*}'`（本轮实测）。

**files**（`:9-13`）：`out/**/*`、`package.json`、`'!**/*.map'`、`'!**/{.eslintrc,.editorconfig,.gitignore,README.md,docs,scripts}'`。只收 `out/` + `package.json`，排掉 sourcemap 与开发期文件；`release/builder-debug.yml` 里实测展开成同样的 4 条，说明没有别处覆盖（本轮实测）。

**asar / compression / npmRebuild**：`asar: true`（`:15`）→ 本轮实测 `release/win-unpacked/resources/app.asar` = 1,433,363 B；`compression: maximum`（`:23`）→ 最高压缩，代价是打包时间明显拉长（7.5.4 风险③）；`npmRebuild: false`（`:24`）→ 跳过原生模块重编译，本工程无原生依赖，纯收益。

**extraResources —— 本章最重要的三行**（`:18-22`，`:17` 是原作者注释「托盘 / 窗口图标要在打包后按绝对路径读到，所以放到 asar 外面」）：

```yaml
extraResources:
  - { from: resources, to: resources, filter: ["**/*"] }
```

`asar: true` 把 `out/` 塞进单文件归档。Electron 给 `fs.*` 打了补丁能穿透，但**原生侧**（`Tray` 的图标加载、`nativeImage.createFromPath` 对 `.ico` 的解码、`LoadImage`）拿到的是「文件系统路径」，asar 内的路径对它们不是真文件。`src/main/tray.ts:217` 的 `new Tray(iconPath)` 与 `src/main/window.ts:28` 的 `nativeImage.createFromPath(p)` 都属此类，所以 `resources/` 必须落在 asar 外。本轮实测生效：

```
release\win-unpacked\resources\
  ├─ app.asar       1,433,363 B
  └─ resources\  ←  extraResources
       icon.ico 195,383 B / icon.png 442,852 B / tray.ico 7,647 B
```

注意这只是「配置生效」的证据，不是「安装包里也这样」的证据（安装包未出，见 7.5.2）。

### 7.1.5 `pnpm-workspace.yaml`

全文 7 行（`pnpm-workspace.yaml:1-7`）：`packages: - .`（`:1-2`）声明单包仓库根；`allowBuilds` 三条（`:4-7`）是 **pnpm 11 拦截机制的放行白名单**：`electron`（`:5`）、`esbuild`（`:6`）、`electron-winstaller`（`:7`）。

为什么需要它 —— `docs/_log.md:145-156` 记了原始症状：

```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: electron-winstaller@5.4.0   （docs/_log.md:148）
```

后果是 `node_modules/electron/dist/electron.exe` 根本不存在（`docs/_log.md:150`）—— `electron` 包的 postinstall 干的就是下载对应平台二进制，被拦掉后 `pnpm dev` 会在「找不到 Electron 可执行文件」上失败，报错不指向根因。

**必要但不充分**。`docs/_log.md:152-156` 记了后续实测：加了白名单仍可能缺二进制，`pnpm rebuild electron` **无效**（`docs/_log.md:153`），有效做法是

```powershell
$env:ELECTRON_MIRROR='https://npmmirror.com/mirrors/electron/'
node node_modules/electron/install.js
```

（`docs/_log.md:154-155`）并留下通用结论：**凡是 pnpm 下 electron/esbuild 二进制缺失，直接跑它自己的 `install.js`，别指望 `pnpm rebuild`**（`docs/_log.md:156`）。本轮实测这台机器上二进制是好的（`node_modules/electron` 45.2.1，用 `dist/electron.exe` 跑过探针，见 7.3.2）。

## 7.2 图标资产管线

### 7.2.1 源图与白底去除

**源图**：`C:\Users\YBY\.dsh\attachments\v1\objects\86\863af5ef753a492d99a16d754a7dffdebba44309b00d444dd2e27a87358e8a9e`，路径硬编码在 `scripts/make-icons.py:5`。本轮实测：存在，1,342,108 B，PNG 魔数 `89504e470d0a1a0a`，**1024×1024**。

**问题**：圆角方块外是纯白底。托盘图标叠在任务栏上、标题栏图标叠在深色标题栏上，白底就是白方块，必须变 alpha=0。

**做法**（`scripts/make-icons.py:12-28`）：

```python
probe = im.convert("RGB").copy()        # :13  在 RGB 副本上做，不脏原 RGBA
MAGIC = (255, 0, 255)                    # :14  品红哨兵色
for xy in [(0,0),(w-1,0),(0,h-1),(w-1,h-1),
           (w//2,0),(w//2,h-1),(0,h//2),(w-1,h//2)]:   # :15  8 个边缘种子点
    ImageDraw.floodfill(probe, xy, MAGIC, thresh=20)   # :17
white = (arr[:,:,0] > 250) & (arr[:,:,1] < 5) & (arr[:,:,2] > 250)   # :22
alpha = np.where(white, 0, 255).astype(np.uint8)                     # :25
am    = Image.fromarray(alpha,"L").filter(ImageFilter.GaussianBlur(0.6))  # :26
out.putalpha(am)                         # :28
```

五个关键点：

1. **在 RGB 副本上 floodfill**（`:13`）。直接在 RGBA 上填品红会污染颜色，`putalpha` 后边缘留一圈品红。
2. **8 个种子点，不是 4 个角**（`:15`）。四角只能吃到「从角上连通过去」的白；圆角方块的上下边中、左右边中露出的白底，只有边中点种子吃得到。
3. **`thresh=20`**（`:17`）容忍白底色偏 —— 实测源图四角是 253/253/253 而不是纯 255（见本节末），阈值太紧会在噪点处漏一片白。
4. **品红哨兵色**（`:14` + `:22`）：让「被吃掉的区域」成为可精确重算的掩码，`R>250 & G<5 & B>250` 只命中品红，不命中画面里任何真实白。
5. **0/255 二值化后 `GaussianBlur(0.6)` 羽化**（`:25-26`）：不羽化则圆角是硬锯齿，缩到 16×16 会糊成一圈脏边；0.6 是「够软但不吃图形」的经验值。

**实测数字**（本轮 Python 复算，只读源图、不写任何文件）：

| 量 | 值 |
|---|---|
| floodfill 吃掉的白底像素 | **36,916 px = 3.52%** |
| 羽化后 `alpha == 0` | 34,599 px = 3.30% |
| 羽化产生的半透明像素（`0<alpha<255`） | 4,828 px |
| 圆角内**保留**的近白像素（`RGB>245` 且未被吃） | 4,215 px = 0.40%，包围盒 `x[386,1023] y[194,869]` |

第一行 **36,916 / 3.52%** 与交接记录完全一致（本轮实测复现）。

**关键判断：为什么 floodfill 不会误伤图内白色** —— floodfill 只吃「与种子点通过 `thresh` 连通」的像素，所以只要图内没有与外部白底**连通**的白区就安全。本轮实测两点佐证：

- 圆角内仍保留 **4,215 px** 近白（上表第 4 行），包围盒 `x[386,1023] y[194,869]`，是角色白腹/白字所在 —— **没被吃掉**。
- 水平中线（`y=512`）上 `alpha>0` 区间是 `x=[0,1023]`，整行不透明：圆角方块左右边缘已贴到画布边，白底只存在于四个圆角区；角色白腹被深色背景整圈包住，与外白底不连通。

**必须记下的细节**：`docs/shots/logo-alpha.png` 四角不是纯 `(255,255,255)`，而是 253/254 一档（本轮实测 `(0,0)` = A0 R253 G253 B253、`(1023,0)` = A0 R254 G254 B254）。这正是 `thresh=20` 与 `>250` 这两个宽松阈值必要的原因 —— 用 `== 255` 会漏。

### 7.2.3 为什么同一个 logo 要放好几个地方

三份文件内容一样（256 与 64 各两份），看着像重复劳动，实际对应**三条互不相通**的取图路径。

**路径一：渲染层 —— 必须走 Vite 资源管线。** `src/renderer/src/components/TitleBar.tsx:13-15` 的注释写得很清楚：

```ts
// 走 vite 资源导入：构建后拿到带 hash 的资源 URL（renderer 的 base 是 './'，
// 用绝对路径 /logo.png 在打包后 loadFile 的 file:// 下会 404）
import logoUrl from '../assets/logo.png'
```

（用于 `src/renderer/src/components/TitleBar.tsx:82` 的 `src={logoUrl}`）

为什么绝对路径会 404：打包后渲染层由 `win.loadFile(join(__dirname, '../renderer/index.html'))` 加载（`src/main/window.ts:127`），协议是 `file://`，其根不是应用目录 —— `/logo.png` 会被解析成 `file:///logo.png`，即盘符根。于是有两种活法：

- **`import` 方式**：Vite 把图挪进 `out/renderer/assets/`、改名为 content hash 文件，并把 import 换成相对 URL。本轮实测产物 `out/renderer/assets/logo-1srejZ5X.png`（130,944 B），`out/renderer/index.html:29-30` 用的正是 `./assets/...` 相对路径。
- **相对路径方式**：`src/renderer/public/logo-64.png` 被 Vite **原样直拷**到 `out/renderer/logo-64.png`（本轮实测 11,643 B），于是 `src/renderer/src/components/SidebarShell.tsx:296` 的 `<img src="./logo-64.png">` 在 `file://` 下解析为 `out/renderer/logo-64.png` —— 命中。

| 位置 | 走法 | 使用者 | 产物 |
|---|---|---|---|
| `src/renderer/public/logo{, -64}.png` | 原样直拷，文件名不变 | `<img src="./xxx.png">` | `out/renderer/logo*.png` |
| `src/renderer/src/assets/logo{, -64}.png` | `import` → hash 重命名 | `TitleBar.tsx:15` 这类 | `out/renderer/assets/logo-<hash>.png` |

（澄清一处易误读：`src/renderer/src/components/MarketTab.tsx:179-190` 的 `ICON_CANDIDATES` 里也有 `'assets/logo.png'`、`'logo.png'`、`'public/logo.png'` 字符串，但那是**市场里远端插件的图标候选路径**，与本项目 logo 无关。）

**路径二：主进程 —— 必须按绝对路径从磁盘读。** 托盘（`src/main/tray.ts:217` `new Tray(iconPath)`）与窗口（`src/main/window.ts:28` `nativeImage.createFromPath(p)`）拿的是文件系统绝对路径，走 Electron 原生侧解码器，不认 Vite、不认 `import`、不认 asar 内伪路径 —— 这决定了 `resources/` 必须 `extraResources` 到 asar 外（`electron-builder.yml:18-22`）。

**路径三：exe 嵌入图标 —— 编译期烧进 PE。** `electron-builder.yml:31` 的 `win.icon: build/icon.ico` 不是运行期读的：electron-builder 把它写成 PE 资源节嵌进 `DSHPluginConsole.exe`（7.3.5 有 0.00% 差异的实测）。所以 `build/icon.ico` 与 `resources/icon.ico` 是两份必须同源的资产，目前靠人工同步（7.6）。

## 7.3 任务栏 / 窗口 / 托盘图标怎么真正生效

现象直观（任务栏显示 Electron 原子图标），但根因与流行说法**是两回事**。

### 7.3.1 改前状态

改前 `createWindow()` 传的是路径字符串 `assetPath('icon.png')`，而 `resources/` 下当时**根本没有 `icon.ico`**。现状从代码读：`src/main/window.ts:42` 的 `const icon = resolveWindowIcon()`，`src/main/window.ts:50` 的 `icon,` 传给 `new BrowserWindow({...})` —— 传的是**对象**不是字符串。`resources/` 现在有三个文件：`icon.ico`(195,383)、`icon.png`(442,852)、`tray.ico`(7,647)（本轮实测）。改前用的 `icon.png` 实测就是 512×512 单帧。

### 7.3.2 隔离 A/B 实测：PNG 是「被忽略」还是「尺寸不对」

交接记录（同一份代码只改图标路径，分别用 `resources/icon.png` 与 `resources/icon.ico` 起 dev 实例，从外部进程用 `WM_GETICON` 读窗口持有的图标句柄）：

| 传入路径 | `ICON_BIG` | `ICON_SMALL2` |
|---|---|---|
| `resources/icon.png`（512×512 单帧） | **512×512** | **512×512** |
| `resources/icon.ico`（多帧） | **48×48** | **24×24** |

（交接记录，本轮未复测 —— 需起 GUI 并从外部进程发窗口消息）

**这条数据推翻了一个流行说法**。「PNG 被 Windows 忽略，所以任务栏退回默认图标」—— 不准。实测里 PNG 路径下 `ICON_BIG` 明确拿到 512×512，Windows 没有忽略它，它只是**照单全收**。

**准确说法是**：PNG 只能提供**单帧**，Electron 把它整张塞进 `ICON_BIG` 与 `ICON_SMALL2` 两个槽位，于是任务栏按钮（需 32 左右）、Alt-Tab（需 48 左右）、标题栏（需 16～24）全拿到一张 512×512，由系统在运行期强行缩小 —— 结果不是清晰小图，而是带缩放糊边的小图，观感上就是「图标不对」。只有**多帧 `.ico`** 才能让 Windows 按目标尺寸**挑一帧**（`build/icon.ico` 带 16/24/32/48/64/128/256，见 7.2.2），`ICON_BIG` 落在 48、`ICON_SMALL2` 落在 24 —— 正是任务栏与标题栏的常规请求尺寸。一句话：**PNG 是「输错了尺寸」，不是「被忽略」**。

**本轮补的实测（一个容易踩的陷阱）**：用 Electron 45.2.1 的 `nativeImage.createFromPath()` 读这几份文件（探针脚本，`app.whenReady()` 后打印，不建窗口）：

| 文件 | `getSize()` | `isEmpty()` |
|---|---|---|
| `resources/icon.ico`（7 帧，最大 256） | **256×256** | `false` |
| `build/icon.ico`（同一份） | **256×256** | `false` |
| `resources/tray.ico`（4 帧，**最大只有 32**） | **256×256** | `false` |
| `resources/icon.png`（512×512） | 512×512 | `false` |
| `src/renderer/public/logo.png`（256×256） | 256×256 | `false` |

（本轮实测，`node_modules/electron/dist/electron.exe` 跑临时探针）

结论：**`getSize()` 对 `.ico` 恒报 256×256，与文件里真实帧集合无关** —— `tray.ico` 最大帧只有 32，`getSize()` 照样说 256。所以 `getSize()` 不能用来判断「这份 ico 能不能用」；可信判据是 `isEmpty()`（「解码器能不能解出东西」），这正好是 `src/main/window.ts:29` 用的判据，`src/main/window.ts:33` 只是拿 `getSize()` 做日志参考。

### 7.3.3 修法（读真实代码）

**第一步：新增 `resolveWindowIcon()`**（`src/main/window.ts:21-38`），返回 `Electron.NativeImage | undefined`：

```ts
function resolveWindowIcon(): Electron.NativeImage | undefined {
  for (const rel of ['icon.ico', 'icon.png']) {   // :22  顺序即优先级
    const p = assetPath(rel)                       // :23
    if (!existsSync(p)) { console.warn(...); continue }     // :24-27  不存在 → 试下一个
    const img = nativeImage.createFromPath(p)       // :28
    if (img.isEmpty()) { console.warn(...); continue }      // :29-32  解析为空 → 试下一个
    console.log('[窗口] 已加载窗口图标：', p, img.getSize()) // :33
    return img
  }
  console.warn('[窗口] 找不到任何可用的窗口图标，回退 Electron 默认图标')  // :36
  return undefined                                  // :37
}
```

四个设计点：① `['icon.ico','icon.png']` 顺序（`:22`）—— `.ico` 是主路径（多帧按尺寸供图），`.png` 只在 `.ico` 缺失/解析为空时兜底（macOS/Linux 用得上），理由写在 `src/main/window.ts:13-19`；② `existsSync` 先判存在（`:24`），避免 `createFromPath` 对不存在路径解码产生噪音错误；③ `isEmpty()` 兜底（`:29`）—— 文件在 ≠ 能解，损坏的 ico 或扩展名骗人的文件都会走到 `continue`；④ 全失败返回 `undefined` 绝不 throw（`:37`）—— 图标是锦上添花，不能让它让应用起不来，而 `undefined` 传给 `BrowserWindow` 的 `icon` 是合法的（回退 exe 本身图标）。

**第二步：`createWindow` 传对象而非字符串**（`src/main/window.ts:42`、`:50`）。传 `NativeImage` 对象时 Electron 直接把图像交给窗口，不再走「路径 → 解码」那条可能按单帧处理的旧路。

**第三步：`ready-to-show` 后补一次 `setIcon`**（`src/main/window.ts:72-80`）：

```ts
win.once('ready-to-show', () => {
  win.show()                    // :73
  if (!icon) return             // :74
  try { win.setIcon(icon) } catch (err) { console.warn(...) }   // :76-78
})
```

为什么要补 —— 上方注释（`src/main/window.ts:66-71`）给了理由：「Windows 创建窗口时用 exe 的嵌入图标填任务栏按钮，构造参数里的 `icon` 有时只作用到标题栏/Alt-Tab；等窗口真正显示出来再 `setIcon` 一次，任务栏那一格才会刷新成我们的 logo」。注意 `win.show()`（`:73`）在 `setIcon()`（`:76`）**之前**：必须等窗口有了实际的任务栏按钮对象，`setIcon` 才有东西可刷。

三层叠加的效果：构造参数打底 → 显示后刷新任务栏 → 任一环失败都只 warn 不崩。

### 7.3.4 `setAppUserModelId` 的位置不是根因

```ts
app.setName('DSH 插件台')                                    // src/main/index.ts:13
if (process.platform === 'win32') app.setAppUserModelId('com.yg.dsh-plugin-console')  // src/main/index.ts:14
```

两行在**模块顶层**，即 `app.whenReady()` 之前执行。代码注释（`src/main/index.ts:7-12`）把理由写全了：「Windows 靠 AppUserModelID 给任务栏按钮分组、并从 exe 读取图标与跳转列表；窗口一旦创建再改这个 ID，任务栏分组的图标不会跟着刷新，只能重启进程才生效。所以放在模块顶层（`app.whenReady()` 之前执行），不要挪进 whenReady 回调里。」

时序对比：`app.whenReady().then(...)` 在 `src/main/index.ts:48` 才开始，`ensureWindow()` 在 `src/main/index.ts:52` 被调 —— AUMID 在 `:14` 就设完了，比建窗口早几十毫秒，**位置完全正确，不是根因**。根因就是 7.3.2 的单帧 PNG。

### 7.3.6 两个真发现

**① dev 实例与打包实例被 Windows 合并成同一个任务栏按钮。** 原因链：dev 时主进程同样执行 `app.setAppUserModelId('com.yg.dsh-plugin-console')`（`src/main/index.ts:14`，这行没有 `app.isPackaged` 判断，dev 也照跑）；打包 exe 用同一个 AUMID（`electron-builder.yml:1` 的 `appId` 与 `:14` 同串）；Windows 的任务栏分组键就是 AUMID → **合并成一个按钮**，图标取先占位者。后果：拿 dev 与打包实例并排对比，会看到「一个按钮、图标时而这样时而那样」的假象，极易误判成「图标加载不稳定」。**验证必须二选一，或按②隔离**。

**② 窗口被隐藏时，任务栏按钮整个消失。** `src/main/window.ts:90-115` 的 close 处理器在「收进托盘」路径上执行 `e.preventDefault()` + `win.hide()`（`:101-102`）。窗口一旦 `hide()`，Windows 把任务栏按钮**整个移除**（不是变灰、不是变暗）。于是：用户以为程序关了（任务栏没按钮），其实进程还在托盘 —— 所以 `src/main/window.ts:104-106` 在第一次隐藏时弹一次通知「程序还在托盘里运行，右键托盘图标可以退出」；排查图标问题时若在 `hide()` 之后截任务栏，会得到「没有任务栏按钮」，被误读成「图标没加载」。这也解释了 `src/main/index.ts:68-72` 的 `window-all-closed`：托盘还在就不退出（`if (hasTray()) return`，`:69`），因为「关窗口」在这个应用里的语义是「收进托盘」。

## 7.4 运行时资源路径三套语义

最容易错的地方：同一个 `resources/` 在三种环境下**绝对路径完全不同**，而渲染层走的是第三条独立的路。

### 路径 A：dev（未打包）

```ts
const base = app.isPackaged
  ? join(process.resourcesPath, 'resources')      // src/main/tray.ts:36
  : join(app.getAppPath(), 'resources')           // src/main/tray.ts:37
return join(base, rel)                            // src/main/tray.ts:38
```

未打包时走 `src/main/tray.ts:37`：dev 下 `app.getAppPath()` 就是**项目根目录**（electron-vite dev 把 `package.json:8` 的 `main` 指到 `out/main/index.js`，`app.getAppPath()` 返回含 `package.json` 的目录）。于是 `D:\项目\DSH\deepseekharness插件台\resources\icon.ico` —— 本轮实测存在，195,383 B。

### 路径 B：packaged

打包后走 `src/main/tray.ts:36`：`process.resourcesPath` 指 exe 旁的 `resources\`，而 `extraResources` 又把 `resources/` 映射成 `resources/resources/`（`electron-builder.yml:19-20`）—— 最终是**两层 `resources`**：

```
release\win-unpacked\resources\resources\icon.ico
```

本轮实测该目录下 `icon.ico`(195,383)、`icon.png`(442,852)、`tray.ico`(7,647) 齐全，与 dev 下同名文件字节一致。

**双层 `resources` 不是 bug，是 `from: resources` / `to: resources` 的必然结果**。若嫌难看想改成 `to: .`，`src/main/tray.ts:36` 的 `'resources'` 拼接就得同步改，否则打包后找不到图标文件 —— 而 `src/main/tray.ts:211-214` 找不到只 warn 后 `return`、不建托盘，于是关窗口直接退出应用，症状看起来像「卸载不干净」。

同一份逻辑被窗口图标复用：`src/main/window.ts:23` 的 `assetPath(rel)` 就是 `src/main/tray.ts:34-39` 导出的函数（`src/main/window.ts:5` 的 `import { assetPath } from './tray'`）—— 窗口与托盘图标共用一套解析，改动只有一处。构建产物原样保留，本轮实测 `out/main/index.js:9568`：

```js
const base = electron.app.isPackaged
  ? (0, node_path.join)(process.resourcesPath, "resources")
  : (0, node_path.join)(electron.app.getAppPath(), "resources");
```

### 路径 C：渲染层（完全另一条路）

渲染层**完全不碰** `assetPath`，走 Vite 资源管线（见 7.2.3）：

| 方式 | 源码 | 构建后 |
|---|---|---|
| `import logoUrl from '../assets/logo.png'` | `TitleBar.tsx:15` | `out/renderer/assets/logo-1srejZ5X.png`（130,944 B），用于 `TitleBar.tsx:82` |
| `<img src="./logo-64.png">` | `SidebarShell.tsx:296` | `out/renderer/logo-64.png`（public 直拷，11,643 B） |

三套语义对照：

| 运行环境 | 写法 | 解析到 | 谁在用 |
|---|---|---|---|
| dev（主进程） | `assetPath('icon.ico')`（`src/main/window.ts:23`） | `<项目根>\resources\icon.ico` | 窗口/托盘 |
| packaged（主进程） | `assetPath('icon.ico')`（`src/main/tray.ts:36`） | `<exe>\resources\resources\icon.ico` | 窗口/托盘 |
| dev（渲染层） | `import logo from '...'` | dev server 的 `http://localhost:<port>/src/assets/logo.png` | 界面 |
| packaged（渲染层） | `import logo from '...'` | `file:///.../out/renderer/assets/logo-<hash>.png` | 界面 |

**最容易犯的错**是把两边互相套用：渲染层若写 `file://` 绝对路径 `/logo.png`，就是 `TitleBar.tsx:14` 注释里那个 404；主进程若想 `import` 一张 png，则需另配 loader —— `externalizeDepsPlugin`（`electron.vite.config.ts:6`）只处理依赖，不管图片资源进主进程 bundle。

### 7.5.4 已知的打包风险

**① `asar: true` 下任何按路径读文件的代码都会失败。** `asar: true`（`electron-builder.yml:15`）把应用代码塞进单文件归档，Electron 给 `fs.*` 打了补丁能穿透，但**原生侧路径读取不行**：`nativeImage.createFromPath`、`Tray` 的图标加载、`LoadImage`、把路径当参数传给外部 exe。当前此类调用只有 `src/main/window.ts:28` 与 `src/main/tray.ts:217`，都已被 `extraResources` 覆盖（`:18-22`）。但这是**当前状态，不是不变量**：以后任何「从 `resources/` 读图标/模板/配置」的新代码都必须走 `assetPath()`（`src/main/tray.ts:34-39`）。排查技巧：dev 正常 + 打包后某功能静默失效 + 控制台一行「找不到 XXX」warn → 先怀疑这条。

**② `extraResources` 只覆盖 `resources/`。** `docs/`、`scripts/`（`electron-builder.yml:13` 显式排除）、`build/` 与任何 `node_modules`（`files` 只收 `out/**/*` 与 `package.json`，`:9-11`）都不在包里。当前代码没有依赖这些（7.1.1 已核无 `dependencies`），但这是「加功能时容易忘」的边界 —— 运行期 `require` 一个未打进包里的 npm 包，就是 `Cannot find module`。

**③ `compression: maximum` 明显拉长打包时间。** `electron-builder.yml:23`。对 250 MB 级 exe（实测 249,947,648 B）+ Electron 运行时做 7z 级压缩，耗时是 `normal` 的数倍。**调试图标/配置时别用 `pnpm dist`，用 `pnpm dist:dir`**（`package.json:15`，无压缩步骤）—— 这也是当前 `release\win-unpacked\` 存在而没有 setup.exe 的原因（7.5.2 ①）。

**④ `npmRebuild: false` 与未来原生依赖冲突。** `electron-builder.yml:24`。当前无原生依赖所以纯收益；一旦引入（如本地 sqlite），这行必须改 `true`，`files`（`:9-13`）也得放行对应 `node_modules` 路径，否则装出来的包会在首次调用原生模块时崩。
