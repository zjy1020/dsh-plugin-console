## 1. 产品定位与它解决的具体痛点

### 1.1 一句话定位

「DSH 插件台」是一个**独立的 Electron 桌面应用**（不是 DSH 插件、不注册进 DSH 的 bundles），它在**本机**管理 DeepSeek Harness（DSH）各 profile 的插件：查看已装、检查更新、升级 / 降级、卸载、从 GitHub 与 npm 自定义安装、浏览社区插件市场、以及导出一份「能装回来」的清单。

出处：`README.md:3`（「管理 DeepSeek Harness（DSH）各 profile 已装插件的独立桌面工具」）、`package.json`（无任何运行时 `dependencies`，全部为 `devDependencies`；`main: ./out/main/index.js`）。

### 1.2 它管的对象：profile 下的「两套账」

这是整个产品立论的基础，也是本工具最核心的可视化对象。

一个 profile 目录（如 `C:\Users\YBY\.dsh\profiles\desktop\`）里有两个地方共同决定「插件状态」：

- `package.json` 的 `dependencies` —— **装了哪些包**（键是包名，值是 spec：`^1.66.5` / `github:o/r` / `link:D:\...`）。
- `package.json` 的 `dsh.profile.bundles` —— **加载列表**（一个有序数组，顺序即加载顺序），**决定 DSH 启动时真正加载哪些插件层**。

两者的差集就是「装了但没加载」，也就是界面上被叫「缺口」的东西。

证据（A/B）：

- `src/main/engine/inventory.ts`（399 行）首部注释直接把这两个来源写为「唯一真相」，并明确「只在 bundles 里、没进 dependencies 的包也会产出一条记录（spec 记空串），这样 UI 上不会有『在加载但看不见』的幽灵包」。
- `docs/_log.md` 记录：bundles 里会出现 `dependencies` 中不存在的官方包（`@deepseek-ai/dsh-base`、`dsh-web-app`、`dsh-headless`），因此**清单数据源必须是两者的并集**。
- `docs/shots/v2-installed.png`（12:15，A）：标题栏读数 `desktop 16 插件 · 18 加载层`；侧栏 PROFILE 区列出三个 profile —— `desktop 16 插件 · 18 加载层`、`headless 0 插件 · 2 加载层 [未初始化]`、`web 7 插件 · 9 加载层`。同张图左下另有 `runtime 0.2.1-rc.5`、`DSH 运行中 8 进程`。
- `docs/shots/v3-shell-01.png`（13:45，A）：改版外壳的状态卡读数为 `插件 16 / 加载层 12 / 缺口 4`，并把 16 个下标画成一条刻度（实心＝在 bundles 内，空心＝被移出）。同一 profile 在 12:15 是 `18 加载层`、13:45 是 `12 加载层`，说明该读数随本机实际状态变化，是实读而非写死。

### 1.3 具体痛点（逐条）

**痛点 1：DSH 自带的插件入口看不到「装了但没加载」。**
DSH 桌面端自己的插件管理在设置页里，命令行侧 `dsh plugin` 也直接拒绝 desktop profile —— `docs/_log.md` 记录实测报错原文：

```
error: profile "desktop" is managed exclusively by the Electron application
```

（来源：DSH 自带 CLI 的 `bin.js` / `rejectElectronProfile`，见 `docs/_log.md`。）也就是说，对最常用的 `desktop` profile，官方 CLI 通道是关死的，改这两处账只能手改 JSON + 手跑 pnpm。

**痛点 2：GitHub 装插件会因为 pnpm 的构建脚本拦截而「静默失败」。**
`docs/_log.md` 第一章第二节记录：pnpm 11 默认拦构建脚本，直接报

```
ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED
```

要求往 `<profile>/pnpm-workspace.yaml` 的 `allowBuilds` 写**带完整 codeload URL 的精确 key**，形如：

```
'dshmarket@https://codeload.github.com/dsh-market/dsh-market/tar.gz/c01a967a...': true
'dshmarket@1.73.8': true
```

写对之后 prepare 真跑，输出 `Build complete in 110ms`；不修则是「装了等于没装、pnpm 什么都不装就退出」。普通用户看不出这层区别，只会看到「装完了但功能没出现」。

**痛点 3：`@latest` 会被供应链冷却悄悄压回旧版，造成「可更新」永远亮。**
同文档记录：`dsh-context` 远端已是 `0.79.0`，装 `@latest` 只装到 `0.78.2`。本工具的对策是先补一次远端查询拿真实版本、再钉精确版本安装（`src/main/engine/versions.ts` 725 行）。

**痛点 4：`cordis.patch.yml` 的外部停用与本工具的停用是两笔账，容易互相打架。**
`README.md:14` 把「是否被 `cordis.patch.yml` 外部停用」列为要展示的状态之一；`docs/_log.md` 第六章确认：patch 层**只读**，本工具自己的停用记录写在 `<profile>/.dsh-console/state.json`（存的是被移出 bundles 前的**下标**，以便原位恢复）。`docs/shots/v2-installed.png`（A）里能看到 `dsh-custom-brand` 一行同时带 `已停用` 与 `PATCH 停用` 两个徽章 —— 两种停用来源被分别标注。

**痛点 5：更新/卸载没有留痕，改坏了回不去。**
`README.md:37` 的流程图写明「改前自动备份 package.json 到 `.dsh-console/backup/`」；`docs/_log.md` 第六章给出备份目录里两样东西：`package.json`、`pnpm-workspace.yaml`，文件名带毫秒时间戳。

**痛点 6：跨机器/跨 profile 重装插件靠人肉记。**
这是第二批需求里「导出清单 + 导入清单」要解决的问题，实现见第 3 章第二批第 7 条与第 4 章第 4.7 / 4.10 节。

### 1.4 与 DSH 自带插件管理、dsh-market 的边界

- **不自己发明写入协议**：`docs/_log.md` 第六章写明 `@deepseek-ai/dsh-plugin-manager/operations` 是「唯一正规写通道」；工具通过动态 `import` 复用官方 `operations.js`，一次拿到 `reconcile()`（bundles 调和）、兼容性门禁（`engines.dsh` + peerDeps 不兼容直接 exitCode 1 且什么都不装）、快照回滚、诊断日志（`<profile>/.plugin-manager/logs/operation-<随机>/pnpm.log`）与 `withFileLock` 跨进程写锁。
- **对 dsh-market 的关系是「逆向对齐」而非依赖**：`docs/market-parity.md` 858 行记录了对手实现的取证（对象 `D:\项目\DSH\_recon\dsh-market`，package name `dshmarket`，version `1.73.8`，git HEAD `c01a967a2603f670795eea7e4e1bd9717e05d3ff`）。插件市场的目录取数直接照搬它的源顺序（见 4.8 节）。
- **不做的事**：不接管 DSH 自身的启动加载逻辑、不改 `cordis.patch.yml`、不碰官方内置层（`@deepseek-ai/*` 在主进程里被判定为不可卸载）。

## 3. 功能清单：六批需求逐条落点

每条给出四行：**需求 → 实现 → 用户怎么用 → 证据**。证据里的截图只写文件名与时间（内容已核对的会标 A）。

### 3.1 第一批（最初 3 条）

#### 3.1.1 显示当前已安装的插件，可以更新

- **实现**：`src/main/engine/inventory.ts`（399 行）读 `<profile>/package.json` 的 `dependencies` ∪ `dsh.profile.bundles`，与 `<profile>/node_modules/<pkg>/` 元数据合流成 `PluginRecord[]`；更新判定在 `src/main/engine/updates.ts`（353 行），只判定不写。执行升级由 `src/main/engine/ops.ts`（1607 行）的 `runOp` 负责。
- **怎么用**：打开应用 → 主区「已安装」tab 看列表 → 行内「更新」按钮（`PluginRow.tsx:113`）或工具栏「更新全部 (N）」。
- **证据**：A —— `docs/shots/v2-installed.png`（12:15）显示 16 行插件，每行带 `NPM`/`LINK`/`FILE` 来源徽章、版本号与「停用 / 目录 / 卸载」操作列，底部 `显示 16 / 共 22`、`4 个已停用`；工具栏存在「检查更新」「更新全部」按钮。B —— `src/shared/ipc.ts` 的 `CH.plugins` / `CH.checkUpdates` / `CH.runOp` 通道存在。

#### 3.1.2 支持卸载

- **实现**：`runOp` 的 `uninstall` 分支调 pnpm `remove`，并同步 bundles；`removable` 由主进程判定（内置或被依赖时为 false）。
- **怎么用**：行内「卸载」→ 两步确认（第二关需输入指定文本）。
- **证据**：B —— `PluginRow.tsx:153-167`（含不可卸载时的两种 tooltip 文案）、`ConfirmDialog.tsx:2` 的「两步确认」注释；`docs/shots/v2-installed.png` 每行都有「卸载」按钮（A）。

#### 3.1.3 自定义安装（输入 GitHub 仓库即可安装）

- **实现**：`src/main/engine/spec.ts`（456 行）把输入归一化成 pnpm spec（`ParsedSpec`），`installPreview` 会拉远端元数据并判定「是不是 DSH 插件」。
- **怎么用**：侧栏「＋ 安装插件」或「安装插件」tab → 智能输入 → 粘贴 GitHub URL / `owner/repo` / npm 包名 → 预检通过后按确定安装。
- **证据**：A —— `README.md:17-19` 列出支持的输入形态（GitHub 仓库 URL、`owner/repo`、npm 包名、`包名@版本`、tarball URL、`link:路径`）；`docs/shots/v2-installed.png` 与 `v3-shell-01.png` 都有「＋ 安装插件」入口。

**关于「NSIS 打包」**：`electron-builder.yml` 配好的是 `nsis` x64、`artifactName: DSH-Plugin-Console-${version}-setup.${ext}`，但 `release/` 目录里**只有 `win-unpacked/`**（含 `DSHPluginConsole.exe`，249 947 648 B）与 `builder-debug.yml`，**没有 setup 安装器**。结论见 5.1 节。

## 4. 主链路功能说明

本节按「用户实际会走的十一条链路」组织，写清入口、底层动作与失败面。

### 4.1 列已装

- **入口**：启动即进「已安装」。
- **底层**：`inventory.ts` 读 `package.json`（`dependencies` + `dsh.profile.bundles` 取并集）+ `node_modules/<pkg>/package.json` + `cordis.patch.yml`（只读）+ `.dsh-console/state.json`（本工具停用态）。
- **产出字段**：`sourceKind`（npm/link/file/git/tarball/workspace/unknown）、`inBundles` + `bundleIndex`、`disabled`、`disabledInPatch`、`builtin`、`removable`、`sizeBytes`、`depsCount`。
- **失败面**：`inventory.ts` 只读、不写、不抛，所有 IO 异常被兜住 → UI 走 `EmptyState`（`PluginList.tsx:73`「主进程没在 DSH_HOME 下找到任何 profile。去设置里确认 DSH_HOME 与安装根是否正确。」）。

### 4.2 检查更新

- **入口**：侧栏「检查更新」/ 工具栏「检查更新」。
- **底层**：`updates.ts` 逐包打 registry 比 latest，只写 `PluginRecord` 的 `latestVersion` / `updateAvailable` / `updateKind` / `updateError` / `checkedAt`，**不做任何写操作**。
- **状态位**：`checkbar`（`role="status" aria-live="polite"`）显示进度；`RuntimeInfo.warnings` 走「警告横幅」展示。
- **失败面**：单包异常折成中文 `updateError`，行内显示「检查失败」徽章（`PluginRow.tsx:70,100`）。

### 4.3 更新（含降级 / 换版本）

- **入口**：行内「更新」（`updateKind` 决定 tooltip）、工具栏「更新全部 (N)」、详情面板或市场详情里的版本选择器。
- **底层**：`ops.ts` 的 `runOp`（`OpKind = update | update-all | install`），最终执行 `pnpm add` 并补 `dsh.profile.bundles`。
- **换版本的三个坑（C，`docs/_log.md` 第七章）**：current 必须用**本地已装版本**而非预览的远端版本；npm 包要传 `rec.name`；摘要文案分三支 —— `已安装 X` / `版本已替换：X 旧 → 新` / `安装命令跑完了，但这个包当前就已经是这个版本，没有变化`。
- **失败面**：`runOp` 把异常吃成 `ok:false` + 中文 message（不外抛）；每次操作都写 `changes[]`（含旧值/新值）供 UI 渲染 diff；`restartRequired` 为真时界面提示「装完插件要重启 DSH 才会加载。」（A，截图可见）。

### 4.4 卸载

- **入口**：行内「卸载」→ 两步确认。
- **底层**：`runOp` 的 `uninstall` → pnpm `remove` → bundles 由 `reconcile()` 自动过滤掉该包（`docs/_log.md` 第三章③）。
- **前置门禁**：`removable === false` 时按钮禁用，tooltip 区分「官方内置包，主进程不允许卸载」与「被其他包依赖，主进程判定不可卸载」。
- **备份**：改前把 `package.json` 复制到 `<profile>/.dsh-console/backup/`（文件名带毫秒时间戳）。

### 4.5 GitHub 自定义安装

- **输入形态**：GitHub 仓库 URL、`owner/repo`、`包名@版本`、tarball URL、`link:路径`、npm 包名（`README.md:17-19`）。
- **预检**：`parseSpec`（`spec.ts` 456 行）→ `installPreview` 拉远端元数据 → 判定 `isDshPlugin`、`alreadyInstalled`、给 `warnings`。判据是 `dsh.bundle.patch`（**不是** `dsh` 字段存在性 —— 第一版用后者会触发 warning `<name> declares no dsh.bundle — installed as a plain dependency, not as a profile layer`，见 `docs/_log.md` 第三章②）。
- **git 版本列表**：走本机 `git ls-remote`（不走 GitHub API），见 3.3.1。
- **失败面**：`link:/file:/workspace:` 不出「挑版本」按钮；预检不过时安装按钮 tooltip 变为「预检没通过，先修输入」（`InstallPanel.tsx:216`）。

### 4.6 npm 安装（两条子链路）

- **搜索 npm**：`registrySearch` 打 registry，命中行可直接装或先「挑版本」。
- **手动 spec**：绕过预检，直接交给 pnpm。
- **安全网**：`Manual spec` 的输入框 `aria-label="pnpm spec"`；预检在 `auto` 与 `search` 两侧默认开启。
- **并发**：`DEFAULT_SETTINGS.concurrency = 6`。

### 4.7 导入清单批量装

- **入口**：安装插件 → 导入清单。
- **流程**：选文件（或粘贴 JSON）→ `importManifest` 解析 → `ManifestPreview{total, present, missing, specs, warnings}` → UI 显示「已安装 N，继续安装会覆盖」「缺 N 个」「导出时已停用」等徽章 → 确认后 `runOp('install-manifest')`。
- **宽容度**：缺 `kind` 的 `{plugins:[...]}` 也认，只给 warning；非本程序导出的 JSON 直接拒绝（`InstallPanel.tsx:720,729`：`清单应该是本程序导出的 JSON 文件。`）。
- **跨 profile 提示**：清单里记录的 profile 与当前不同时，界面显示「（导出时用的是 profile「X」）」（`InstallPanel.tsx:737`）。

### 4.8 插件市场安装

- **取数（A）**：目录 = npm 包 `dsh-plugin-catalog` 里的 `plugins.json`，源顺序 —— ① `<settings.registry>/dsh-plugin-catalog/latest` → `dist.tarball` → gunzip → 解 tar → `package/plugins.json`；② `https://registry.npmmirror.com` 同法；③ `https://awesome-dsh-plugin.com/plugins.json`。每个源 try/catch，成功即停；全失败给中文 error 并列出试过哪些源、各自为何失败。内存缓存 + inflight 去重 + 磁盘缓存，**只在抓到非空 plugins 时才写盘**（半截数据不许覆盖好目录）。二进制走 electron `net.fetch`（同一 session，代理生效），异常降级 `node:https` 直连。
- **实测性能与规模（A，探针产物）**：目录总量 **8281**；宫格 4 列（`_grid1.json` / `_grid2.json`：columns 4、templateCols 243.333px×4、cards 48、cardH 158、domNodes 744→830）；虚拟滚动（`_virt1.json`：firstCardMs 25、interactiveMs 529、gridH 352058、maxScrollTop 351485、cardsAfterOpen 48；`_virt9.json`：skeletonMs 21、firstCardMs 312、top48WithIcon 1）；**滚动延迟从 27751 ms 降到 62 ms**（`_lag1.json` → `_lag2.json`，后者 `longTasks: []`）。
- **图标现实（A）**：`_iconrate.json` 48 张卡稳定 `decoded 9 / monogram 39`（约 18.75% 有图），有图的全部是「仓库子目录形态」条目（如 `OpenViking#examples/dsh-memory-plugin`、`dsh-web#packages/dsh-task-board`）。`_guess2.json` 的猜图回退实测 **`hitRate: "0/12"`、`hits: 0`、errors 108**（9 个候选路径全 error）。
- **能力标注**：卡片上有 `capabilities` 静态扫描徽章（`MarketTab.tsx:1088`，tooltip `静态扫描声明会用到的能力：${c}`）；`deprecated` 条目标注建议替换为 `entry.replacement`。

### 4.9 启动 / 退出 DSH

见 3.2.5。补充：`dshproc.ts` 的三个已知坑写进了文件头（exe 名带空格所以按名找更稳；必须删子进程 env 里的 `ELECTRON_RUN_AS_NODE`；对外函数一律不抛）。`DshStatus` 含 `pids`，界面会显示进程号列表（`DshControl.tsx:129`）。

### 4.10 导出清单

- **入口**：已安装 tab 工具栏「导出清单」（主入口）/ 设置 → 清单（并列入口）。
- **口径**：只导 `installed && removable`（第三方已装），跳过 `link:/file:/workspace:`，跳过的记进 `skipped[]`。
- **防重复点击**：`PluginList.tsx:34` 注释——保存对话框是系统模态，连点时导出按钮要挡住。
- **产物**：`ManifestFile{kind:'dsh-plugin-console/manifest', version:1, exportedAt, dshVersion, profile, plugins[]}`。

### 4.11 附属链路：停用 / 启用、修复重装、取消、去重

- **停用 / 启用**：行内按钮（`PluginRow.tsx:139`）。停用 tooltip「从 `dsh.profile.bundles` 里移除，重启 DSH 后生效」；启用 tooltip「重新加入 `dsh.profile.bundles`，重启 DSH 后生效」。**只动 bundles，不动 `cordis.patch.yml`**，原下标记进 `.dsh-console/state.json` 以便原位恢复。
- **修复（重新安装）**：`node_modules` 里缺包时按钮由「停用」换成「重新安装」（tooltip `用 spec「<spec>」重新安装`），对应 `OpKind.repair`。

- **尺寸统计**：`PluginDetail.tsx:258`「重新用 `deep:true` 拉一次列表，统计 `node_modules` 占用」→ `sizeBytes`（按需，不在默认扫描里）。
