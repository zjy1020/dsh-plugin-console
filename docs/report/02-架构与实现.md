# 02 架构与实现

本章描述「DSH 插件台」的实际代码结构：进程分层、契约边界、每个模块的导出签名与职责、一次写操作从点击到落盘的完整路径，以及并发、降级、安全三类横切关注点。

## 0. 证据约定

- 本章每条结论都追溯到仓库里的真实文件，形式为 `路径:行号`（多行用 `路径:起-止`）。
- 行号取自本次撰写时的文件快照。仓库中的 `src/` 全部为 TypeScript 源码，没有构建产物被引用。
- 凡是代码里读不出、或本次未实测的，一律写「未核实」，不做推断性描述。
- 相对路径以仓库根 `D:\项目\DSH\deepseekharness插件台` 为基准。
- 项目根**不是 git 仓库**（`git log` 返回 `fatal: not a git repository`），所以本章不涉及提交历史；无法用 diff 佐证「某字段是哪次改动加的」，版本演进的判定依据是 `scripts/patch-contract-v*.mjs` 与 `src/shared/types.ts` 中的分节注释。

## 1. 技术栈、构建与类型边界

### 1.1 运行时与工具版本

全部依赖都声明在 `devDependencies` 里（`package.json:17-29`），工程**没有 `dependencies` 段** —— 运行期依赖只有 Electron 自带的 Node/Chromium，业务代码零第三方运行时库：

| 组件 | 版本 | 出处 |
| --- | --- | --- |
| Electron | `^45.2.1` | `package.json:22` |
| electron-vite | `^6.0.0` | `package.json:24` |
| React / ReactDOM | `^19.3.1` | `package.json:25-26` |
| TypeScript | `^5.9.3` | `package.json:27` |
| Vite | `^8.3.5` | `package.json:28` |
| electron-builder | `^26.18.0` | `package.json:23` |
| @vitejs/plugin-react | `^6.1.2` | `package.json:21` |
| @types/node | `^24.7.0` | `package.json:18` |

`package.json:2-8` 给出包标识：`name` 为 `dsh-plugin-console`，`productName` 为 `DSH 插件台`，`private: true`，`main` 指向 `./out/main/index.js`，`author` 为 `YG`。

### 1.2 刻意不使用 ESM

`package.json` 中**没有 `"type": "module"`**（对照 `package.json:2-16` 的全部顶层键）。这是有意为之：主进程与 preload 输出 CJS，绕开 Electron 在 preload 场景下对 ESM 的限制。`tsconfig.node.json` 的 `module` 是 `ESNext`、`moduleResolution` 是 `bundler`（`tsconfig.node.json:5-9`），即「源码写 ESM 语法、产物打 CJS」这条常规组合。

### 1.3 三个 tsconfig 与两个类型检查命令

- `tsconfig.json` 只有 4 行：`files: []` + `references` 指向其余两个（`tsconfig.json:1-4`），本身不编译任何文件。
- `tsconfig.node.json`（21 行）：`lib: ["ES2023"]`、`types: ["node"]`、`strict: true`、`noEmit: true`、`composite: true`、`skipLibCheck: true`（`tsconfig.node.json:6-11`），include 覆盖 `src/main/**/*.ts`、`src/preload/**/*.ts`、`src/shared/**/*.ts` 与 `electron.vite.config.ts`（`tsconfig.node.json:20`）。
- `tsconfig.web.json`（21 行）：在上一份基础上加 `DOM`、`DOM.Iterable` 两个 lib 与 `jsx: "react-jsx"`，去掉 `types`（`tsconfig.web.json:6-7`），include 覆盖 `src/renderer/**/*.ts`、`src/renderer/**/*.tsx`、`src/shared/**/*.ts`、`src/preload/*.d.ts`（`tsconfig.web.json:20`）。
- 两者都设了 `strict: true` 与 `skipLibCheck: true`（`tsconfig.node.json:8`、`tsconfig.node.json:11`；`tsconfig.web.json:8`、`tsconfig.web.json:11`）。
- 类型检查是一条串起来的命令：`tsc --noEmit -p tsconfig.node.json && tsc --noEmit -p tsconfig.web.json`（`package.json:13`），**两份必须都 exit 0**，否则整条 script 非零退出。

拆分的关键收益在 include 的边界上：`src/shared/` 被两份同时包含，`src/preload/*.d.ts` 只进 web 侧，`src/main/**` 只进 node 侧。也就是说渲染层拿不到 `node:*` 类型，主进程拿不到 DOM 类型 —— 契约层被两份配置夹在中间，任何一侧都不能偷偷引入另一侧的平台类型。

### 1.4 构建与打包

构建配置只有 17 行（`electron.vite.config.ts:1-17`）：

- `main` 与 `preload` 都挂 `externalizeDepsPlugin()`（`electron.vite.config.ts:6`、`electron.vite.config.ts:9`）。
- `renderer` 挂 `@vitejs/plugin-react`，并把 `chunkSizeWarningLimit` 提到 2000（`electron.vite.config.ts:13-14`）。

构建脚本为 `electron-vite build`（`package.json:11`），打包为 `electron-vite build && electron-builder --win --x64 --config electron-builder.yml`（`package.json:15`），另有 `--dir` 免安装包版本（`package.json:16`）。

打包侧的关键选择（`electron-builder.yml`）：

- `appId: com.yg.dsh-plugin-console`、`output: release`、`buildResources: build`（`electron-builder.yml:1`、`electron-builder.yml:6-7`）。
- `asar: true`（`electron-builder.yml:15`），但 `extraResources` 把 `resources/` 原样放到 asar 外（`electron-builder.yml:18-20`）—— 托盘与窗口图标在运行时按绝对路径读取，打进 asar 就读不到。
- `npmRebuild: false`（`electron-builder.yml:24`）：本工程没有原生模块，跳过 rebuild。
- Windows 目标为 NSIS x64，`executableName: DSHPluginConsole`（`electron-builder.yml:32`），`oneClick: false`（`electron-builder.yml:36`），安装界面语言 `zh_CN` / `en_US`。

## 2. 目录分层与冻结契约

### 2.1 三层 + 一份契约

```
src/shared/      types.ts（数据契约）  ipc.ts（通道名 + window.dsh 接口 + DEFAULT_SETTINGS）
src/preload/     index.ts（contextBridge 暴露 window.dsh）  index.d.ts
src/main/        index.ts（生命周期 / 单实例锁）  window.ts（无边框窗口）  ipc.ts（glue）
                 tray.ts  wallpaperProtocol.ts
src/main/engine/ 23 个模块（全部业务）
src/renderer/    App.tsx + components/（22 个 .tsx）+ lib/store.ts + styles/（11 个 css）
```

`src/shared/types.ts:1-6` 的头部注释把这条边界写死：类型是唯一真相，main/engine 产出它们，preload 透传，renderer 只消费，任何改动都要同时改 engine 与 renderer。

### 2.2 契约冻结的三处同步

契约层的改动必须同时落在三处，缺一处就会出现「渲染层能调到但主进程没 handler」或反过来的静默失败：

1. `src/shared/ipc.ts` —— 加通道名到 `CH` / `EV` 常量（`src/shared/ipc.ts:38-97`）。
2. `src/preload/index.ts` —— 在 `contextBridge.exposeInMainWorld` 的对象上补对应方法。
3. `src/main/ipc.ts` —— 用同一个常量名注册 `ipcMain.handle`。

`src/shared/ipc.ts:1-4` 的注释把这套分工写明：main 侧用 `CH` 注册 handler，preload 侧用 `CH` 桥接，renderer 侧只认 `window.dsh`。

### 2.4 三种「账」

插件的状态被拆在三个地方，运行期语义完全不同（`docs/_log.md:12-21`）：

| 账本 | 位置 | 含义 |
| --- | --- | --- |
| 依赖账 | `<profile>/package.json` 的 `dependencies` | 真正装了什么 |
| 加载账 | `<profile>/package.json` 的 `dsh.profile.bundles` | 启动时按数组顺序加载哪些层 |
| 停用账 | `<profile>/cordis.patch.yml` | DSH 自己的配置覆盖 / 停用清单（只读，不写） |

外加本工具自己的私有账本 `<profile>/.dsh-console/state.json`，用来记住「我们把它从 bundles 摘掉时它在第几位」（3.5 节、5.12 节）。

`bundles` 里会出现 `dependencies` 里没有的包（`@deepseek-ai/dsh-base`、`dsh-web-app`、`dsh-headless` 这类随 runtime 发布的层），所以清单的数据源必须是两者的并集，不能只看 `dependencies`（`docs/_log.md:12-21`）。

## 4. 主进程骨架

主进程加桥接层共 7 个文件、合计 1136 行：`index.ts`(73) / `window.ts`(143) / `tray.ts`(303) / `ipc.ts`(301) / `wallpaperProtocol.ts`(164) / `../preload/index.ts`(143) / `../preload/index.d.ts`(9)。分工是一条直线：`index.ts` 管生命周期，`window.ts` 管窗口，`tray.ts` 管托盘，`ipc.ts` 只转发，`wallpaperProtocol.ts` 管一条自定义协议。

模块间的依赖方向（只允许向下，不出现环）：

```
index.ts ──> window.ts ──> ipc.ts（wireWindowState）──> engine/*
   │            └────────> tray.ts（assetPath / isQuitting）──> ipc.ts（broadcast）
   ├──> tray.ts
   └──> wallpaperProtocol.ts ──> engine/settings、engine/wallpaper
```

`window.ts:4-5` 从 `./ipc` 引 `wireWindowState`、从 `./tray` 引 `assetPath` / `isQuitting`；`tray.ts:22` 反过来从 `./ipc` 引 `broadcast` —— 两者是同一个 `ipc.ts`，不构成环。

### 4.1 index.ts：生命周期与单实例锁

1. `app.setName('DSH 插件台')`（`src/main/index.ts:13`）。注释（`src/main/index.ts:7-11`）写明理由：Windows 靠 AppUserModelID 给任务栏按钮分组并从 exe 读图标，窗口一旦创建再改就不刷新，只能重启进程，所以放在模块顶层、不挪进 `whenReady` 回调。

3. `registerWallpaperScheme()`（`src/main/index.ts:20`）。注释（`src/main/index.ts:16-19`）说明协议权限声明必须在 ready 前，Chromium 只在协议注册表初始化时读这一份。

`whenReady()` 里的启动顺序固定为 4 步（`src/main/index.ts:48-52`）：`registerIpc()` → `installWallpaperProtocol()` → `installAppMenu()` → `ensureWindow()`。前两个顺序不能换：`installWallpaperProtocol()` 注册的 handler 依赖 `engine/settings` 与 `engine/wallpaper` 可读，而 `registerIpc()` 里已经挂了壁纸相关的 13 个 IPC 通道（`src/main/ipc.ts:192-241`），先有 handler 再有协议 handler 是它们的共同前提。`activate`（`src/main/index.ts:54-60`）在没有窗口时重建、否则唤回。

### 7.1 预检：只读，不写盘

### 7.7 bundles 调和：谁写、谁不写

19. **自建通道下我们自己补**：`declaresBundle(pkg) || forceBundle` 为真 → `bundles.addBundle(profileDir, name)`（不带 `at`，追加末尾）（`ops.ts:956-985`）；为假就只打一行「装了但没进加载列表：它的 package.json 没有声明 dsh.bundle.patch」（`ops.ts:963-967`）。
20. 无论哪条通道，写 bundles 都经过 `bundles.setBundles`（`bundles.ts:142`）→ 原子写（tmp + rename，失败清 tmp，`bundles.ts:82-112`），并且**写前自动备份** package.json 到 `.dsh-console/backup/`（`bundles.ts:90`、`bundles.ts:119-135`）。

### 7.8 回传与 UI 更新

21. `opInstall` 返回 → `ops.runOp` 返回 → handler **先** `broadcast(EV.opDone, result)`（`src/main/ipc.ts:89`）**再** `return result`（`src/main/ipc.ts:90`）。
22. 渲染层因此同时从两条路收到「结束」：
   - 返回值路径：`store.ts:871-872` 的 `await` → `dispatch({type:'opEnd', value:result})`。`installSpec` 把 `runOp` 的返回值直接 return 给组件，但组件只用它做「装完关抽屉」这类收尾。
   - 事件路径：`store.ts:791-796` —— `opEnd` + toast（`result.ok ? 'success' : 'error'`，标题「操作完成」/「操作失败」，正文 `result.message`）+ `loadPlugins(profile)` 重拉插件列表。
23. 日志是流式、先到的：`EV.opLog` → `store.ts:787-789` → `state.logs`（进度行会按 `progress && last.opId === line.opId` 折叠成一行，`store.ts:412-414`；上限 `MAX_LOGS`，`store.ts:417`）→ `<LogDrawer>` 渲染。
24. 收尾提示：`restartRequired: true`（`ops.ts:1016`）由 `OpResult` 带出，界面据此提示「重启 DSH 才会加载」，重启按钮走 `actions.restartDsh()`（`store.ts:1107-1122`，先确认再 `CH.restartDsh`）。

### 7.9 其它 kind 的差异

- `update`：目标钉精确版本（`ops.ts:1161`），并多一层「冷却豁免 + 静默压版本补偿」（见第 9 章）。

## 8. 并发与取消

### 8.1 三处并发控制

| 位置 | 机制 | 行号 |
| --- | --- | --- |
| 更新检查 | worker pool，默认并发 6，钳到 1..16，`onProgress` 回传 | `updates.ts:126` |
| 官方通道 | 官方 `withFileLock(<profile>/package.json)`，等锁上限 120 秒 | `ops.ts:360-365`、`dshpm.ts:216-217` |
| 自建通道 | **无全局互斥**，靠 opId 分组管句柄 | `pnpm.ts:55-56`、`pnpm.ts:130` |

自建通道不互斥是刻意的：它在语义上等价于「用户自己开两个终端跑 pnpm」，而真正需要串行的是同一个 profile 的 package.json —— 那件事官方通道用文件锁做了，自建通道没做（第 12 章记录）。

### 8.2 cancelOp 的两把刀

- 入口只有一个：日志抽屉里的「取消」按钮（`LogDrawer.tsx:78`，显示条件 `op !== null && op.opId !== null`，`LogDrawer.tsx:39`）→ `actions.cancelOp()`（`store.ts:1092-1105`）→ `api().cancelOp(opId)`（`store.ts:1099`）→ `CH.cancelOp`（`src/main/ipc.ts:93`）→ `ops.cancelOp`。
- `ops.cancelOp`（`ops.ts:79-84`）只有三行，两边都捅、取或：

```ts
if (!opId) return false
const killed = pnpm.killOp(opId)         // 自建通道：杀子进程树
const aborted = dshpm.abortOfficial(opId) // 官方通道：AbortController.abort()
return killed || aborted
```

- **第一把刀** `pnpm.killOp`（`pnpm.ts:370-383`）遍历该 opId 名下所有句柄：句柄表的 key 是 `<opId>##<seq>`（`pnpm.ts:130`），`getHandles(opId)` 用前缀匹配 `key === opId || key.startsWith(opId + '##')`（`pnpm.ts:358`），所以一次 op 里前前后后起的多条命令会被一起收掉。每个 `RunHandle.kill()` 在 win32 上先 `spawn('taskkill', ['/pid', String(pid), '/T', '/F'], { windowsHide: true, stdio: 'ignore', shell: false })`（`pnpm.ts:202-206`）再 `proc.kill()`（`pnpm.ts:212-216`）。`/T` 是必须的：pnpm 自己还会拉子进程，只杀父进程会留下孤儿。
- **第二把刀** `dshpm.abortOfficial`（`dshpm.ts:229-239`）从模块级 `activeSignals: Map<string, Set<AbortController>>`（`dshpm.ts:226`）取出该 opId 的所有 controller（跳过已 aborted 的，`dshpm.ts:234`），调 `abort(new Error('用户取消了操作'))`（`dshpm.ts:236`）。注册在 `dshpm.ts:278-285`，`finally` 里注销（`dshpm.ts:317-326`）。
- **为什么必须是两把刀**：官方通道根本不是子进程 —— 它是 `import()` 进同一进程的模块函数调用（`dshpm.ts:150`、`dshpm.ts:309`），`taskkill` 对它无效；而官方只认 `options.signal`（注释 `dshpm.ts:273`）。反过来，`AbortController` 也杀不掉自建通道的 `spawn` 出来的进程。
- UI 侧：`cancelOp` 返回 boolean，true → toast「已发送取消信号 opId <id>」，false → toast「取消没有被接受，操作可能已经结束」（`store.ts:1100-1101`）。措辞是「已发送」不是「已取消」—— 真正结束仍以 `EV.opDone` 为准。
- **一个可观察的边界**：操作刚开始的一瞬间点取消会得到「当前没有可取消的操作」（`store.ts:1094-1097`），因为 `state.op.opId` 还停在 `null`（`store.ts:868`），要等第一条日志把它回填（`store.ts:418-420`）。

### 8.3 超时也是「取消」

两条通道的超时机制完全不同，因为官方库没有整体超时：

- 自建：`spawnProcess` 里挂 `setTimeout`，到点 `proc.kill()` 并往日志里塞一个**固定串** `[超时，已终止]`（`pnpm.ts:284-292`）；默认 `DEFAULT_TIMEOUT_MS = 10 分钟`（`pnpm.ts:51`）。上层靠 grep 这个串判定 `timedOut`（`ops.ts:250`）—— 这是「进程被我们自己杀了」与「pnpm 自己失败」的唯一区分点。
- 官方：注释（`dshpm.ts:273`）写明「官方只认 `options.signal`，超时得我们自己做成中止信号」—— `new AbortController()`（`dshpm.ts:274`）+ `setTimeout(() => controller.abort(...), timeoutMs)`（`dshpm.ts:275`），再用 `AbortSignal.any([controller.signal, opts.signal])`（`dshpm.ts:276`）把「超时」和「用户取消」合成一个信号。默认 `timeoutMs = 10 分钟`、`idleTimeoutMs = 5 分钟`（`dshpm.ts:270-271`）。

### 8.4 确认弹窗是单槽位，不是队列

`state.confirm` 只能挂一个请求：`requestConfirm` 会先把上一个 resolve 成 false 再挂新的（`store.ts:652-657`）。`confirmBusy` 期间，取消 / Esc / 再次确认全被挡（`store.ts:661`、`store.ts:676`）。这套「抢占 + 序号」的写法（`store.ts:688-701`）是为了避免长操作的弹窗被下一个请求换掉之后，旧 Promise 永远不 resolve。

### 8.5 两个 4 秒轮询

`dshproc.watch` 被订阅了两次：`src/main/ipc.ts:174`（推 `EV.dshStatus` 给界面）和 `tray.ts:252`（重建托盘菜单），都传 4000ms。是否在 `dshproc` 内部去重，见第 12 章。

## 9. 错误与降级策略

### 9.1 总原则

引擎层的第一条设计原则是「任何异常都吃成 `ok:false` + 中文 message，不许把栈抛到 IPC 层」。六个取数模块各自在文件头把这条写死：`net.ts:6`、`updates.ts:8`、`versions.ts:11`、`market.ts:18`、`gallery.ts:7`、`icon.ts:7`。渲染层再兜一层 `toMessage(err)`（`api.ts:34`）。结果就是：**界面永远不会因为一次网络抖动而白屏**，最坏情况是某条记录上多一个「更新失败」标记。

### 9.3 自愈重试的三条纪律

`runPnpmAddish`（`ops.ts:268-313`）的重试是**有界**的：每种修法最多用一次，最多两轮。注释（`ops.ts:256-266`）把这两类故障定性为「环境政策性失败，不是用户输入错了」，所以修的是**环境文件**而不是命令。

要修的 key 一律**从 pnpm 自己的输出里抠**，不是我们猜的：`parseGitPrepareKeys`（`profileYaml.ts:295-337`）认三种形态（`allowBuilds` 示例块、`git-hosted package … needs to execute build scripts`、`Ignored build scripts:`）。写回时还有个细节 —— `profileYaml` 是零依赖行扫描器，只认得「我上次写的那一行」，不认识完整的 YAML，所以新增项的插入位置分 flow map（写前面，`profileYaml.ts:140-142`）与块形式（写后面，`profileYaml.ts:163`）两种，写法见 `profileYaml.ts:306-333`。

### 9.4 错误信息是怎么变成中文的

`errorSummary(log)`（`ops.ts:486-494`）先用 `isErrorLine` 挑错误行（正则含 `ERR_` / `ELIFECYCLE` / `ENOENT` / `EACCES` / `EPERM` / `EEXIST` / `404 Not Found` / `ETARGET` / `error`，以及中文「版本不存在」「不存在该」「无效的包名」，`ops.ts:478-484`），取最后 4 行；一条都挑不出来就取整段日志的最后 6 行（`tailLog`，`ops.ts:471-476`）。外面再套一层场景化前缀：「安装失败（exit N）：…」「更新失败（exit N）：…」「安装超时，已终止」。

### 9.5 官方通道的三类失败文案各管一段

`dshpm.ts:255-267` 分别给：找不到模块 →「未找到 DSH 官方的 dsh-plugin-manager/operations 模块」；加载抛错 →「加载官方 operations 模块失败：<message>」；缺导出 →「官方 operations 模块没有导出 runProfilePnpm」—— 前两类都被 `runPnpmOp` 的 catch 接住转成降级（`ops.ts:233-240`），第三类同理。

## 10. 安全边界

### 10.1 渲染层发不出任意网络请求

`src/renderer/index.html:24-27` 的 CSP 原文：

```
default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https: dshwp:;
```

**没有 `connect-src`**，于是它由 `default-src 'self'` 兜住 —— `fetch` / `XHR` / `EventSource` / `WebSocket` 一律只能打回本页 origin。这条约束的后果是全项目最重要的架构事实：渲染层**所有**远程取数都必须绕道主进程（`CH.marketList` / `CH.pluginGallery` / `CH.versions` / `CH.registrySearch` / `CH.pluginIcon` / `CH.registryLookup` / `CH.proxyTest` …），主进程再走 Electron `net.fetch`（`net.ts:217-222`）—— 于是代理设置（写进 Electron session，`net.ts:83-104`）对所有远程请求天然生效，渲染层根本不需要知道代理存在。

`img-src` 放开的 `https:` 是刻意的例外（理由注释在 `src/renderer/index.html:9-13`）：插件作者托管在 GitHub 的图标与截图必然是远程地址，只写 `'self' data:` 会让所有远程图被静默拦掉、卡片全变首字母占位；图片不能执行脚本，SVG 走 `<img>` 也是隔离子集，再配合 `referrerPolicy="no-referrer"` 不把本机信息带出去。

`img-src` 里的 `dshwp:`（理由注释 `src/renderer/index.html:15-17`）与 `wallpaperProtocol.ts` 的 `bypassCSP: false`（`wallpaperProtocol.ts:41`）是配对的：协议不绕 CSP，所以 CSP 里必须显式放行，否则壁纸全黑。

### 10.2 preload 是唯一那座桥

`contextIsolation: true`（`window.ts:59`）+ `nodeIntegration: false`（`window.ts:60`）+ 只通过 `contextBridge.exposeInMainWorld('dsh', api)` 暴露一个对象（`src/preload/index.ts:143`）→ 渲染层拿不到 `require` / `process` / `ipcRenderer`，类型上只认 `src/preload/index.d.ts:3-7` 声明的那一个 `window.dsh`。

`sandbox: false`（`window.ts:58`）是这条边界上的一个**已知放宽**：preload 拥有完整 Node 能力，因此 preload 代码必须当作可信代码对待。目前它只做参数透传和一次同步 `webUtils.getPathForFile`（`src/preload/index.ts:122-128`），没有任何文件系统或网络调用。`webSecurity: true`（`window.ts:61`）保持同源策略不被关掉。

### 10.3 外部打开与导航

- 新窗口一律拒绝：只有 `^https?://` 交给 `shell.openExternal`，其余 `{ action: 'deny' }`（`window.ts:117-120`）。
- `CH.openExternal` 在 main 侧**再校验一次** `^https?:\/\//i`（`src/main/ipc.ts:114`）—— 双重校验，因为渲染层传进来的字符串从定义上就不可信。
- `CH.revealPath` 只接三种情形：存在且是文件 → 资源管理器选中；存在 → `shell.openPath`；不存在 → `false`（`src/main/ipc.ts:97-111`）。没有通配、没有命令拼接。

### 10.4 `dshwp://` 只读壁纸目录

四层校验，缺任何一层都能被绕（`wallpaperProtocol.ts:61-97`）：

1. **入口白名单**：`thumb` 的 id 与 `files` 的 rel 都拒 `\0`，`thumb` 额外拒 `/` 与 `\`（`wallpaperProtocol.ts:126`、`wallpaperProtocol.ts:136`）—— 堵住「把 id 当路径拼」的写法。
2. **只允许相对路径**：`files` 拒绝对路径（`wallpaperProtocol.ts:138`）；`thumb` 的 id 白名单化后才 `join(root, 'thumbs', id + '.png')`（`wallpaperProtocol.ts:130`）。
3. **前缀校验一**：`relative(root, resolved)` 必须非空、不以 `..` 开头、不是绝对路径（`wallpaperProtocol.ts:68-71`）。
4. **前缀校验二**：`realpathSync` 之后再判一次前缀（`wallpaperProtocol.ts:79`），防 symlink 逃逸（注释 `wallpaperProtocol.ts:59`）—— 没有这一层，往壁纸目录里放一个指向 `C:\Windows` 的符号链接就能读出去。

越界与不存在**返回同一个 404**（`wallpaperProtocol.ts:62-65`），不区分二者，避免把这个协议当成目录探测面。协议是只读的：`protocol.handle` 里只有 `net.fetch(file://…)`，没有任何写分支。

### 10.5 profile 目录名的路径穿越

`env.getProfileDir(name)` 只做一件事：`join(getDshHome(), 'profiles', safeSegment(name))`（`env.ts:388-390`）。防线在 `safeSegment`（`env.ts:79-84`）：

```ts
String(name ?? '').trim().replace(/[\\/]/g, '').replace(/\.\./g, '')
```

它是**净化**而不是**报错**：`../../etc` 会变成 `etc`，`a/b` 会变成 `ab`。`listProfileNames()` 用同一把尺子过滤目录名（`env.ts:399`），所以界面上根本出现不了会穿透的名字。所有下游写操作（`ops.ts:845-856`、`ops.ts:847`）只认这个函数产出的路径字符串。

### 10.6 子进程不经过 shell

自建通道的 `spawn` 显式 `shell: false` + argv 数组（`pnpm.ts:220-226`），杀进程用的 `taskkill` 同样 `shell: false`（`pnpm.ts:205`）。包名与 spec 只作为 argv 的单项传递，不存在「拼进命令行字符串」这回事 —— 即使用户在来源框里贴 `; rm -rf /`，pnpm 也只会把它当成一个非法包名报错。

子进程环境由 `childEnvFor()`（`ops.ts:406-430`）构造：`env.buildChildEnv()` 打底 + 代理四件套 + `NO_PROXY=localhost,127.0.0.1,::1` + `npm_config_registry`，并强制 `CI=1`、`NO_COLOR=1`（注释 `ops.ts:401-405` 说明官方 `execution: 'service'` 下先走 `scrubbedParentEnv()`，所以 PATH 必须自己塞进 `options.env`）。node / pnpm 一律取 DSH 自带运行时（`pnpm.ts:5` 头注释），不走系统 PATH。

### 10.7 写操作的原子性与可回滚

| 目标文件 | 写法 | 备份 | 行号 |
| --- | --- | --- | --- |
| `<profile>/package.json` | tmp + `renameSync`，失败清 tmp | 写前自动备份到 `.dsh-console/backup/package.json.<ISO 毫秒>.json`（文件名带毫秒防同秒覆盖） | `bundles.ts:82-112`、`bundles.ts:119-135` |
| `<profile>/pnpm-workspace.yaml` | tmp（带 pid）+ `renameSync` | 改前备份 `.bak`（带时间戳） | `profileYaml.ts:69-83`、`profileYaml.ts:55-67` |

### 10.8 信任边界小结

| 边界 | 可信侧 | 不可信侧 | 实现 |
| --- | --- | --- | --- |
| 渲染层 → 网络 | 主进程 | 渲染层页面 | `index.html:26` 无 `connect-src`；远程取数全走 IPC |
| 渲染层 → 主进程 | 主进程 | `window.dsh` 里传进来的字符串 | `openExternal` 白名单（`src/main/ipc.ts:114`）、`revealPath` 三分支（`src/main/ipc.ts:97-111`）、`getProfileDir` 净化（`env.ts:79-84`） |
| 协议 → 文件系统 | 壁纸目录 | 任意 URL | 双层前缀校验 + 404 不区分（`wallpaperProtocol.ts:61-97`） |
| 主进程 → 子进程 | pnpm / node | 包名与 spec | `shell: false` + argv 数组（`pnpm.ts:220-226`） |
| 自己 → DSH 的账 | DSH | 本工具 | `cordis.patch.yml` **只读**；写 bundles 走官方 `reconcile()` 优先 |
| 引擎 → IPC | 主进程 | 引擎异常 | 每个 engine 模块「永不抛到 IPC 层」 |
