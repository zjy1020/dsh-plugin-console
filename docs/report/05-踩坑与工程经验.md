## 5.2 A 组：Windows + Electron

### A1　`ELECTRON_RUN_AS_NODE` 让 Electron 退化成 Node 跑

**现象** 启动后窗口永远不出现，日志尾部两行：
```
TypeError: Cannot read properties of undefined (reading 'setName')
Node.js v24.22.1
```
第一行像「某个对象没初始化」，很容易顺着 `setName` 追代码；**第二行才是真凶** —— 说明当前进程跑的是 Node 24，不是 Electron。

**根因** DSH 桌面端（宿主 Electron 应用）在自己的环境里设置了 `ELECTRON_RUN_AS_NODE`，我们 spawn 子进程时 `process.env` 被整体继承，于是**自己的 Electron 可执行文件被当成纯 Node 解释器启动**：不创建 `app`、不创建窗口、不注册 `app.whenReady()`，`app` 是 `undefined`，`app.setName(...)` 直接抛，抛完进程退出并打印 Node 版本。可怕之处在于：报错位置（`setName`）与根因位置（环境继承）**完全不在一处**。

**修法** 在 `src/main/engine/dshproc.ts:317-327` 的 `childEnvForDsh()` 里统一清洗，而不是在每个 spawn 点手写：
```ts
const out = { ...process.env }
delete out['ELECTRON_RUN_AS_NODE']
delete out['ELECTRON_NO_ATTACH_CONSOLE']
delete out['ELECTRON_FORCE_IS_PACKAGED']
delete out['ELECTRON_ENABLE_LOGGING']
```
源码注释（`dshproc.ts:312-315`）原文保留：**关键：删掉 ELECTRON_RUN_AS_NODE —— 有它在，Electron 会被当成纯 Node 跑，界面永远出不来（我们踩过这个坑）**。启动脚本侧同步兜底：`Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue`。

**验证** 两种口径都要过：① 启动日志不再出现 `Node.js v24.22.1` 这种 Node 版本尾巴，且出现窗口初始化日志（`[窗口] 已加载窗口图标： ... { width: 256, height: 256 }`）；② 在宿主环境里显式 `$env:ELECTRON_RUN_AS_NODE=1` 再启动，**行为仍正常** —— 这才证明是代码在清洗，不是「我碰巧站在一个干净终端里」。

### A2　单实例锁没释放导致新实例静默退出

**现象** `Stop-Process` 杀进程后**立刻**再启动：新进程 `alive=False`，**没有任何报错、日志、弹窗**，就像双击没反应。

**根因** `src/main/index.ts:39` 的 `app.requestSingleInstanceLock()` 拿不到锁就走 `:41` 的 `app.quit()`。上一个进程刚被强杀，它持有的 Electron/Chromium profile 级锁还没被系统回收，新进程拿锁失败 → 干净退出。**这是设计行为，所以不报错**。注意同时看 `:43` 的 `app.on('second-instance', () => revealWindow())`：前一个实例还活着时，第二个实例是**把前一个唤到前台**，排查时要区分这两种情况。

**修法** 杀掉实例后**等 4~5 秒**再启动；自动化脚本里写成固定模板：
```powershell
Stop-Process -Id $pid -Force -ErrorAction SilentlyContinue
Start-Sleep -Seconds 5      # 不是 1 秒，不是 2 秒
```

**验证** 连跑 3 轮「kill → sleep 5 → start」，每轮确认：新进程 `alive=True`；有新进程 stdout 日志（那两行窗口/托盘日志）；DevTools 端口重新可连且 uuid 与上一轮不同（`DevTools listening on ws://127.0.0.1:9333/devtools/browser/<uuid>`）。

### A3　pnpm 11 默认拦构建脚本 → electron 二进制没下载

**现象** 装完依赖后 `node_modules/electron/dist/electron.exe` **不存在**，pnpm 输出：
```
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: electron-winstaller@5.4.0
```

**根因** pnpm 11 把「运行依赖的构建脚本」当成需要显式授权的动作（默认不跑 `postinstall`/`prepare`）；而 electron 的二进制**恰好在 postinstall 里下载**（`node_modules/electron/install.js`），不跑就没有 exe。

**修法** 一条链，前几步全是失败记录 —— 别重复走：第 1 步在 `pnpm-workspace.yaml` 授权（`allowBuilds: electron/esbuild/electron-winstaller: true`）；第 2 步重跑 `pnpm install` —— **实测仍不重跑 postinstall**，只打 `Already up to date` ❌；第 3 步 `pnpm rebuild electron` —— **实测无效** ❌（**别指望 `pnpm rebuild`**）；第 4 步（**最终有效**）直跑包自己的安装脚本：
```powershell
$env:ELECTRON_MIRROR = "https://npmmirror.com/mirrors/electron/"
$env:HTTP_PROXY  = "http://127.0.0.1:65535"
$env:HTTPS_PROXY = "http://127.0.0.1:65535"
node node_modules/electron/install.js
```
`ELECTRON_MIRROR` 是必须的：官方源在这台机器上经常挂住，镜像 + 代理才稳。同一手法对 `esbuild` / `electron-winstaller` 通用：找 `node_modules/<pkg>/install.js` 直跑，比跟 pnpm 斗智快。

**验证** `Test-Path "node_modules\electron\dist\electron.exe"` → True，且 `node_modules\electron\dist\electron.exe --version` → `v45.2.1`。两条都过再往下走，别相信「install 没报错」= 装好了。

### A4　150% 缩放显示器上截图必须先做 DPI awareness

**现象** 150% 缩放的显示器上，`GetWindowRect` + `CopyFromScreen` 抓出来的图是「左上角裁一块」或「右半区纯黑」。我一度把它当成**前端布局溢出 bug** 去查 CSS，浪费了时间。

**根因** 进程**不是 per-monitor DPI aware**，Win32 返回的窗口矩形是**被缩放换算过的逻辑坐标**（150% 下 1 逻辑像素 = 1.5 物理像素），而你截的是物理像素表面 → 坐标系错位 → 裁切/黑边。另外 GPU 合成窗口用 `CopyFromScreen` 抓的是屏幕像素，被裁/被遮区域就是黑的。

**修法**（`scripts/screenshot.ps1`）三件事，顺序不能乱：① **先宣告 DPI 感知，且必须在任何窗口/GDI API 之前**：`[Win32Shot]::EnableDpiAwareness()`（内部 `SetProcessDpiAwarenessContext(new IntPtr(-4))`，`-4` = `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`）；放在取 hwnd 之后调就已经晚了。② **取真实可见边框**：`DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS /* = 9 */, ...)`，失败才回退 `GetWindowRect`。③ **优先抓窗口自身内容**：`PrintWindow(hWnd, hdc, PW_RENDERFULLCONTENT /* = 2 */)`，让 DirectComposition/GPU 合成窗口也能画出内容，失败再退 `CopyFromScreen`。同源坑见 B1：**Electron GPU 合成窗口第一帧经常是黑的**，所以 `-Repeat 2` 连拍用第二张。

**验证** 截图四边完整（无半边黑、无内容偏移）；与 CDP 自截图交叉验证一致（`scripts/cdp-eval.mjs --shot` → `Page.captureScreenshot { format:'png', fromSurface:true, captureBeyondViewport:false }`）；DPI 100% / 150% 两种缩放都不裁边。

### A5　PowerShell 的两个坑

**现象 + 根因 + 修法** ① **`&` 调外部命令时参数被啃掉**：`& npm view electron version` 传进 npm 时参数被 PowerShell 的绑定/解析吃掉（路径带空格、参数像 `-` 开头时尤其明显）。修法：套一层 `cmd /c` 并点名 `.cmd` —— `& cmd /c "npm.cmd view electron version"`、`& cmd /c "pnpm.cmd -v"`；只写 `pnpm` 可能命中 `pnpm.ps1`，又绕回 PowerShell 的参数解析。② **用反引号转义 template literal 做字符串替换会失败**：想拼 `` `translateY(${x}px)` `` 这种 TSX 片段，用 PowerShell 反引号转义构造替换串，最后得到的源码不是你想要的（反引号在 PowerShell 里是转义字符，与 JS 模板字面量语义打架）。修法：**别用 PowerShell 做源码精确替换**，改用 Node 脚本（`scripts/patch-*.mjs`）—— 这直接催生了 D3 那套补丁脚本方法论。

**验证** 每条都有「改前失败、改后成功」的最小复现：`& cmd /c "pnpm.cmd -v"` 能打印 `11.8.0`；补丁脚本跑完后 `pnpm typecheck` 通过且只有预期的一处文本改动。

### A6　JSDoc 注释里写 `*/` 会提前闭合块注释

**现象** 一次编译炸出 28 条连锁报错，开头是 `dshpm.ts(13,61): error TS1443` 与 `TS1161 Unterminated regular expression literal`。

**根因** 文件头 JSDoc 里写了一个日志路径 `operation-*/pnpm.log`。其中 `*/` 是**块注释结束符**，注释在这一行被提前闭合，后面的中文文案全变成代码 → 语法错误 → 解析器一路错乱（所以有 28 条，且报错位置与真实位置不在一起）。

**修法** 改文案，别在 JSDoc 里出现 `*/`；要写通配路径就写 `operation-<随机>/pnpm.log`（现在 `dshpm.ts:1-25` 就是这个写法）。

**验证** `pnpm typecheck`（= `tsc --noEmit -p tsconfig.node.json && tsc --noEmit -p tsconfig.web.json`）退出码 0，且 `TS1443`/`TS1161` 不再出现。教训：**注释里绝不能出现 `*/`**，`/**` 同理。

### A7　Windows 任务栏图标：多帧 `.ico`、AUMID 与「隐藏窗口」

本组含**一个常见误传**和**两个真发现**。

**现象** 打包后任务栏按钮显示 electron.exe 默认图标，不是我们的 logo。**误传纠正**：流传的说法是「PNG 被 Windows 忽略」，**这是错的**。准确说法是「**PNG 只能提供单帧**」—— 任务栏走 `ICON_BIG` 通道，系统需要从多帧图标里按尺寸挑帧（16/24/32/48/256…）；只给一张 512×512 时 `WM_GETICON` 会把 `ICON_BIG` 和 `ICON_SMALL2` **都撑成 512×512**，于是任务栏上要么被强行缩放得很难看、要么退回 exe 默认图标。

**真发现 1（尺寸正常了）** 换成多帧 `resources/icon.ico`（`scripts/make-icons.py` 产出 16/24/32/48/64/128/256）后，`WM_GETICON` 读到 `ICON_BIG = 48×48`、`ICON_SMALL2 = 24×24`，即系统开始按尺寸挑帧。取证说明：这组测量是当时**一次性手工探测**得到的，现在 `scripts/` 里**没有**相关代码（grep `WM_GETICON|ICON_BIG|ICON_SMALL2|GetClassLong` 无匹配），本章按战斗卡记录引用。实现侧 `src/main/window.ts` 的 `resolveWindowIcon()` 按 `['icon.ico','icon.png']` 顺序找、**优先 `.ico`**（注释 :16-19 就是上面那段机制）；四条可 grep 的日志：`[窗口] 已加载窗口图标：` / `[窗口] 窗口图标文件不存在，跳过：` / `[窗口] 窗口图标解析为空（文件损坏或格式不支持），跳过：` / `[窗口] 找不到任何可用的窗口图标，回退 Electron 默认图标`。另外 `:72` 在 `ready-to-show` 时又补一次 `win.setIcon(icon)`，注释 :66-71 解释：**Windows 创建窗口时用 exe 嵌入图标填任务栏按钮，构造参数里的 icon 有时只作用到标题栏/Alt-Tab，等窗口真正显示再 setIcon 一次，任务栏那格才刷新。**

**真发现 2（AUMID 相同被合并）** Windows 靠 **AppUserModelID** 给任务栏按钮分组。dev 实例与打包实例用了同一个 AUMID，系统就把两个窗口**合并成一个任务栏按钮**，看起来像「图标不对」或「少了个窗口」。`src/main/index.ts:14` 的 `app.setAppUserModelId('com.yg.dsh-plugin-console')` 注释（:8-11）写明**必须在任何 BrowserWindow 创建之前调用**：窗口创建后再改 ID，分组和图标都不会刷新，**只能重启进程**。

**真发现 3（窗口隐藏 → 按钮消失）** `minimizeToTray` 默认 `true`，`close` 被拦下改成 `win.hide()`，此时**任务栏按钮连同图标一起消失**。早期「没有图标」的截图里**有一半是这个假象**。所以取证纪律是：**抓任务栏图标前必须先 `ShowWindow` 唤醒窗口**（`scripts/foreground-app.ps1` 就干这个：按命令行里的 `-Tag dsh-probe-9334` 找 electron.exe，再 `ShowWindow(9)`/`BringWindowToTop`/`SetForegroundWindow`）。

**修法汇总** ① 图标用多帧 `.ico`（`build/icon.ico` 由 electron-builder 嵌进 exe，`resources/icon.ico` 供窗口图标）；② `setAppUserModelId` 放在所有窗口创建之前；③ `ready-to-show` 补 `setIcon`；④ 取证前 `ShowWindow` 唤醒。

**验证** 启动日志出现 `[窗口] 已加载窗口图标： <绝对路径>\resources\icon.ico { width: 256, height: 256 }`；A/B 图对比存 `docs/shots/`：`ab-png-taskbar-full.png` / `ab-ico-taskbar-full.png` / `ab-png-windowicon.png` / `baseline-electron-exe-icon.png` / `packaged-exe-icon.png` / `ref-ico-32.png` / `ref-png-32.png` / `taskbar-icon-dev.png` / `taskbar-icon-packaged.png` / `_crop-taskbar-packaged.png` / `_crop-three-icons.png`；打包版也要再验一遍（`packaged-window.png`、`packaged-pid36592-window-icon.png`）。

### A8　托盘存在时 `window-all-closed` 不能退出

**现象** 加了托盘后关掉主窗口应用直接退出、托盘图标跟着没了，「最小化到托盘」形同虚设。**根因** Electron 默认：所有窗口关闭 → `window-all-closed` → 框架默认 `app.quit()`。**修法** `src/main/index.ts:68-72` 的 `window-all-closed` 里判断托盘存在则 `return`；`:64` 的 `before-quit` 里 `setQuitting(true)`，让 `close` 处理器知道「这次是真退出」不要再拦。`close` 拦截在 `src/main/window.ts`：读 `minimizeToTray`（**默认 true；读设置抛错也按 true**），`e.preventDefault(); win.hide()`，并首次弹 `new Notification({ title: 'DSH 插件台', body: '程序还在托盘里运行，右键托盘图标可以退出。' })`。**验证** 关窗口 → 进程仍在（`Get-Process` 查得到）、托盘图标在；右键托盘退出 → 进程消失、`before-quit` 路径走到。

## 5.3 B 组：Chromium / CDP / 截图

### B1　Electron GPU 合成窗口的第一帧经常是黑的

**现象** 静帧截图整块黑或局部黑。**根因**（部分定位）GPU 合成路径下窗口首帧还没把 surface 提交给合成器，`CopyFromScreen`/`PrintWindow` 都可能抓到未合成完成的表面；属 Chromium 合成时序，无公开稳定保证。**修法** 评审静帧**必须连截两张、取第二张**（`scripts/screenshot.ps1` 默认 `-Repeat 2` 即为此）。**验证** 同一窗口连拍 3 张，第 2、3 张一致且非黑；仍有黑块则改用 CDP 截图交叉确认（见 B2）。

### B2　窗口被遮挡时 CDP 截图是空表面，且 `requestAnimationFrame` 根本不回调

**现象** 窗口被别的窗口压住时：`Page.captureScreenshot` 截出来是**空表面（13KB 空图）**；页面里 `requestAnimationFrame` **不回调**（`rafFired=false`）；滚动赋值很便宜（`assignMs: 0`）但视觉更新永不发生。`docs/_scroll3.json`：
```json
{"assignMs":0, "napMs":426, "rafFired":false, "rafMs":1996,
 "transformAfter":"matrix(1, 0, 0, 1, 0, 0)", "rawRequests":243, "rawPending":0,
 "dom":745, "cardImgs":3, "monoIcons":45}
```
**根因** Chromium 对**不可见/被遮挡**窗口停掉渲染管线：合成帧不产出、rAF 被挂起。这不是 Electron 的 bug，是渲染器可见性（occlusion）策略。它同时毁掉两件事：**截图取证**与 **rAF 节流的正确性**（后者见 C2）。**修法** 固定采样序列：`杀掉实例 → 等 5 秒（A2）→ 清 ELECTRON_RUN_AS_NODE（A1）→ 启动 → 等 9 秒 → 立刻截/立刻求值`，外加 `scripts/foreground-app.ps1` 把窗口 `ShowWindow(9)` 抬到前台（其注释原文：**窗口被压住时 CDP 截出来是黑屏**）。**验证** 同一段滚动探针，遮挡时 `rafFired=false`、前台化后 `rafFired=true`；`_lag1.json`（27.8 秒）与 `_lag2.json`（62ms）就是同批差异的产物。

### B3　`location.reload()` 会把已有的 CDP WebSocket 连接弄挂

**现象** 探针脚本里执行一次 `location.reload()` 后脚本**一直挂着不退出**（既不报错也不返回），后续 `Runtime.evaluate` 永不 resolve。**根因**（根因未定位到 Chromium 内部，但行为可复现）重载替换了渲染进程的 execution context，而 `Runtime.evaluate` 绑在旧 context 上；连接没断，但求值请求没有活上下文来回答 → 请求悬死。**修法** 不重载；需要重载才能复现的场景改成「重启应用再截」，即走 B2 序列。**验证** 改重启后脚本正常返回并退出，不需要再 `job_kill`。

### B4　CSP 静默拦掉远程图片（靠双路对照才定位）

**现象** 插件图标与市场卡片图标**全部回落成首字母占位**（大写字母 mono 方块），看起来像「市场里就没有图标」或「图标解析逻辑坏了」。`docs/_icon2.json` 现场：
```json
{ "csp": "default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;",
  "remoteImgTest": { "result": "加载失败（onerror）" },
  "hasMono": true, "monoText": "A", "hole": false }
```
**根因** `src/renderer/index.html` 的 CSP 是 `img-src 'self' data:;` —— **不允许 `https:`**。插件作者的图标托管在 GitHub（`raw.githubusercontent.com`），于是每个远程图标都被 CSP **静默拦掉**（`onerror`，浏览器控制台之外几乎没有痕迹）；组件拿到的只是「加载失败」，很正常地走了首字母兜底。这一刀难在：「图标全变字母块」有 4 个都能解释它的假设 —— ①CSP 拦了 ②URL 猜错了 ③网络不通 ④组件逻辑 bug。

**定位手法：同一个 URL 用 `<img>` 与 `fetch` 双路测**（`scripts/probe-icon-sanity.js`，27 行，就三件事）：① 读 CSP 原文 `document.querySelector('meta[http-equiv="Content-Security-Policy"]')?.content`；② 同一个远程 URL 放进 `<img>` 听 `load/error`；③ 同一个 URL 用 `fetch()` 打一次。结果 **`<img>` 失败、`fetch` 报 `Failed to fetch`，而 CSP 原文里 img-src 没有 https** —— 三路证据同时指向 CSP，而不是 URL 猜错（URL 猜错的话 `fetch` 会拿到 404 之类的确定答案）。

**修法** 放开 `img-src`：`img-src 'self' data: https: dshwp:;`。`dshwp:` 是主进程 `wallpaperProtocol.ts` 注册的本地壁纸协议（壁纸原图几十兆，走 IPC 转 data URL 会撑爆内存；该协议只允许读壁纸目录内文件，越界 404）。**注意一条有意保留的边界**：`connect-src` **仍只允许 `'self'`** —— 渲染层不允许发任意网络请求，所有远程取数必须走主进程。代价是渲染层 `fetch` 远程 URL 会一直 `Failed to fetch`（`MarketTab.tsx:209` 注释原文：**renderer 的 connect-src 只有 'self'，fetch 会 Failed to fetch**），所以图标探测只能靠 `<img>` 的 `load/error` 链式回退。

**验证** `docs/_iconnet.json`（修复后）记录 CSP 已含 `img-src 'self' data: https:;`，四路 `<img>` 测试：声明的 icon → `load 192x192`、猜的候选 → `load 32x32`(785ms)、公共图 → `load 288x288`、**不存在路径 → `error`**。第四路故意留 error 作对照 —— 证明「能加载」不是把 CSP 整体关掉了，而是精确放开 `https:`。补充验收：`cardImgs 5 / cardDecoded 5`；`docs/_iconrate.json` 48 张卡 `imgTags 9 / decoded 9 / mono 39 / empty 0`（7 秒内稳定、无一空洞）。

### B5　React 状态更新是异步的

**现象** 用 CDP 合成 DOM 事件（点分类、敲搜索框）后**立刻**读 DOM，读到旧状态：卡片数没变、footer 文案没变、列表还是上一批。**根因** React 19 的 `setState` 异步批处理：事件处理函数返回后 React 才调度渲染，而 CDP 的 `Runtime.evaluate` 之间没有「等一帧」的概念。**修法** 合成事件与读 DOM 之间**等一拍**：等「时间」用 `setTimeout`（33ms 级），等「渲染」用双 rAF —— 但注意 B2，**窗口必须可见**否则 rAF 不来，那就只能用 setTimeout。**验证** 数值可重复：`categoryMs 12–48ms`、`searchMs 237–253ms`、`searchClearMs 231–260ms`，同一动作连跑 3 次数值同量级、结论一致。

### B6　CDP 合成 DragEvent 拿不到真实文件路径

**现象** 用 CDP 合成拖拽事件验证「拖壁纸 → 导入」，合成的 `DataTransfer` 里 `File` 是造出来的，主进程侧 `webUtils.getPathForFile()` 返回**空**。**根因** Chromium 出于安全，只有**真实用户拖拽**产生的 `File` 才带系统路径元数据；脚本合成的 `File` 是纯内存 Blob，没有路径可查。**这不是产品 bug**。**修法** 把 CDP 拖拽测试的**目标降级**：只验证覆盖层 `.wpdrop` 的渲染与显隐这一半，导入链路改走真鼠标或直接调 IPC（`window.dsh.*`）。**验证** `scripts/probe-wpdrop.js` 的注释就写明「合成 File 拿不到真实路径」；验收口径写两句：「覆盖层显隐 ✅ 由 CDP 验证；导入链路 ⚠️ 不由 CDP 验证」。

### B7　自定义协议必须在 `app ready` 之前声明

**现象** 壁纸走自定义 scheme 时请求被拦或走错分支。**根因** `src/main/index.ts:20` 的 `registerWallpaperScheme()` 调用点注释（:17-18）：**壁纸协议必须在 app ready 之前声明权限，ready 之后再调就晚了，Chromium 只在协议注册表初始化时读这份声明** —— `registerSchemesAsPrivileged` 类声明只被读一次。**修法** 所有 `registerXxxScheme` 放模块顶层、`app.whenReady()` 之前。**验证** 启动日志无协议报错；壁纸生效（`docs/shots/v3-wallpaper-01/03/04.png`）；越界读（协议目录之外的文件）返回 404 而不是内容。

### C1　8281 条目录 + 无限增长的 DOM = 卡

**现象** 市场页打开就自动加载 144 张卡 / DOM 2088；连续滚到底 12 次后：

| 指标 | 修复前 | 说明 |

**验证**（`docs/_virt*.json`，阈值写进 `scripts/probe-market-virt.js`）

### C2　`requestAnimationFrame` 节流在窗口被遮挡时彻底失效

**现象** 旧实现是「scroll 回调里 rAF 节流 + 90ms 兜底计时器」，实测**27.8 秒**才跟上滚动：
```json
{"transformChangeMs": 27751, "footerChangeMs": 27751, "scrollEvents": 1,
 "timerDelayMs": 0, "longTaskTotal": 0,
 "transformAfter": "matrix(1, 0, 0, 1, 0, 59500)", "cards": 36}
```
（`docs/_lag1.json`；`longTaskTotal: 0` 说明**不是主线程忙**，就是没被调度。）

**根因** 同 B2：窗口被遮挡/最小化时 rAF 不回调。滚动视觉更新挂在 rAF 上，就等于挂在「窗口是否可见」上 —— 窗口不可见时视觉更新被无限期推迟，用户回来看到的是「半天前的位置」。**修法** 滚回调里**同步算区间**，不套 rAF。源码注释（`MarketTab.tsx:548-579`）原文：**直接在 scroll 回调里同步算区间，不套 rAF —— 算一次只是读两个 rect 再比几个数（不做布局写入），而窗口被遮挡/最小化时 rAF 根本不回调，实测套 rAF 会让窗口慢一拍甚至一两秒才跟上，快速滚动就会看到空白。** 关键约束：`computeRange()` **只读**（读 rect、比数）、**不写布局**，所以同步执行也不触发强制同步布局。

**验证** `docs/_lag2.json`：`transformChangeMs 62`、`footerChangeMs 62`（`timeline` 里 t=62 完成）—— **27.8 秒 → 62ms**。`probe-market-scroll3.js` 还分开量「赋值耗时（`assignMs`）」与「定时器延迟」，避免把两个指标混在一起。

### C3　卡片里逐张做网络图标解析会把渲染饿死

**现象** 早期实现是每张卡自己发起「猜图标」探测：每屏 17 个候选 × 三次网络探测，实测**滚一格 14.6 秒**。

**根因** 无界并发。每个候选最坏要等几百毫秒到几秒（实测单候选 586–765ms 级，见 `docs/_guess1.json` / `_known.json`），而卡片逐张自己发起 —— 网络队列被塞满、结果乱序回来、同一个仓库被反复探好几遍，主线程被回调轮番打断。

**修法**（`MarketTab.tsx` :206-216 起的探测队列）：① **全局有界队列** `ICON_PROBE_CONCURRENCY=4`、`ICON_CANDIDATE_TIMEOUT_MS=2500`、`ICON_PROBE_QUEUE_MAX=24`；② **按「仓库 + 子目录」缓存** —— `iconCache` / `iconPending` 两个 Map，同仓库只探一次（`pumpIconQueue()` / `enqueueIconProbe()` / `tryIconUrl()` / `probeIcon(repo, sub)`）；③ **卡片先出首字母，探到再换图**（不阻塞渲染）；④ 探测 URL `https://raw.githubusercontent.com/${repo}/HEAD/${candidate}`，候选表 `ICON_CANDIDATES` / `ICON_CANDIDATES_SUB`（+`ICON_SUB_ROOT_FALLBACK=4`）；⑤ 卡片图标改用**纯 `<img>` 的 `load/error` 链式回退**，**不在 JS 里 fetch**（原因见 B4：`connect-src` 只有 `'self'`）。

**验证** 滚动流畅（虚拟滚动验收同步覆盖 `scrollLoopMs 2654–2723ms`）；图标覆盖 `docs/_iconrate.json` 48 卡 `imgTags 9 / decoded 9 / mono 39 / empty 0`（**empty 0** 是关键 —— 没有「一直空着不落位」的洞）。命中率要诚实记录：`docs/_guess1.json` `declaredIcon 478 / total 8281 / guessPool 7803`（**只有 5.8% 的插件声明了图标**，其余 7803 条只能靠猜）；`docs/_subicon.json` `top48 48 / top48SubForm 2 / byStars48SubForm 26 / byStars48Declared 1 / sampled 10 / subHits 5 / rootHits 0` —— 命中的都是 `packages/<x>/icon.svg` 这种**子目录**形态，**仓库根一个都没命中**；`docs/_known.json` 两个对照样本：`dsh-effort-slider-universal` 第一个候选 `assets/icon-180.png` 就命中（706ms），`dsh-folder-launcher` 前 8 个候选全 error、**第 9 个** `assets/icon.svg` 才命中（662ms）。这组数字说明「猜」收益有限、成本不低，队列必须**有界 + 可缓存**，否则就是那 14.6 秒。

### C4　`useLayoutEffect` 量元素位置做「玻璃滑块」

**现象** ① 一进页面玻璃滑块**从顶部滑下来**（像动画）；② 窗口 resize 后位置对不上。**根因** ① 滑块用 `transform: translateY()` 定位，初始 `top` 是 0 或上次的值，**首帧**如果带 CSS 过渡，浏览器就把「从旧位置到新位置」当动画播一次；② 位置是量出来的（依赖布局），尺寸变化后必须重量。**修法**（`src/renderer/src/components/SidebarShell.tsx`）`measure()`（:208）放进 `useLayoutEffect`（:222）—— 在**浏览器绘制前**量，避免闪一下；用 `firstPaint` ref（:123）标记首帧，首帧给滑块加 `.gl-slider--instant` 类**关掉过渡**（:402），量完立刻 `firstPaint.current = false`（:225）；`resize` 时重测（:231-234）；依赖数组含 `state.plugins.length`（:228）—— 列表条目数变了也要重量。**验证** 录首帧：滑块**不动画**、直接出现在正确位置；改窗口宽度后滑块仍对齐选中项（round-trip ≥3 次）。

### C5　同特异性 CSS 规则被拆到两处 → 改一处必须同时看另一处

**现象** 改 `.prow` 的 grid 声明后视觉没变化；或改视觉声明后布局跳了。**根因** `.prow` 在 `src/renderer/src/styles/components.css` 里出现**两次**：`:744`（与 `.plist__head` 合写的**布局/栅格**声明 `grid-template-columns: minmax(0,1fr) 116px max-content`）与 `:818`（**视觉**声明 min-height/border/background/cursor/transition）。两处特异性相同，**靠书写顺序决定谁生效**；分开写本身没问题（好读），但「只改其中一处」会得出「改了没用」的错误结论。**修法** 当成纪律而非 bug 修：`.prow` 相关改动一次看两处（先 `grep '\.prow'` 看命中行号），要么两处都改、要么做一次合并整理（本项目选择保留分块 + 注释）。**验证** CDP 读回计算样式：`getComputedStyle(document.querySelector('.prow')).gridTemplateColumns` 期望 `minmax(0px, 1fr) 116px max-content`（浏览器会规范化成具体数值）。

## 5.5 D 组：工程方法与协作流程

### D1　绝不在真实 profile 上做写操作测试

**做法（最值得抄的一条）** 写操作测试全在一个**一次性临时 profile** 上跑：`C:\Users\YBY\.dsh\profiles\dsh-console-selftest`，内容 `{ "name": "dsh-profile-selftest", "dependencies": {}, "dsh": { "profile": { "bundles": [] } } }`；跑完全流程后 `Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh\profiles\dsh-console-selftest"`。**并且每次测试前后都核对真实 profile 的账** —— 必须始终是同一组数字：`desktop bundles=18 deps=16`（`docs/_ready1.json` 的侧栏 dump：「desktop 16 插件 · 18 加载层」）。

**为什么必须这样** 这个工具会**写用户的 profile**（`package.json` + `cordis.patch.yml` + `pnpm-lock.yaml`）。一旦写坏真实 profile，用户的 DSH 直接起不来 —— 而这类 bug 在临时 profile 上 100% 可复现。**用一个空 profile 换掉「用户数据被写坏」的风险，纯赚。**

**验证** 测试脚本首尾各跑一次 profile 核对、打印两行 `deps=16 / bundles=18`，两次一致才判通过；临时 profile 目录测后确实不存在（`Test-Path` → False）。

### D2　契约层（`src/shared/`）改动必须同步三处

**现象** 改了 IPC 契约后出现两种症状之一：编译不过；或编译过了、运行时**静默失效**（按钮点了没反应、回调永不触发）。**根因** 一次契约改动要落到**至少三处**：① `src/shared/types.ts`（类型）；② `src/shared/ipc.ts`（频道常量 `CH`，:38 起，payload 类型）；③ `main` 侧 `ipcMain.handle(CH.xxx, ...)`（`src/main/ipc.ts`）**+ `preload` 侧 `contextBridge` 桥接**（`src/preload/index.ts`）。漏第三处的 preload 一侧最阴：主进程注册了、渲染层也能调到 `window.dsh.xxx`，但那是 `undefined`，报错点离改动点很远。`src/shared/ipc.ts:1-4` 头注释就是这条纪律的成文版：**main 侧用 CH 注册 handler，preload 侧用 CH 桥接，renderer 侧只认 `window.dsh`**。

**修法** 契约一次性设计完整（见 5.7）；补丁脚本**分开写**：`scripts/patch-contract-v5.mjs` 打 types/ipc/main，`scripts/patch-contract-v5-preload.mjs` 打 preload —— 该脚本头部注释记录了原因：「契约层 v5 —— preload 桥接（单独一段，因为 patch-contract-v5.mjs 的 preload 锚点写错过一次）」。**验证** `pnpm typecheck` 通过 **且** 在 CDP 里直接调 `window.dsh.<新方法>()` 能拿到真实返回（跑通完整 IPC 链路，而不是只编译过）—— 应用带 `--remote-debugging-port=9333` 启动，`scripts/cdp-eval.mjs` 在页面里 eval。

### D3　一次性补丁脚本比手改安全，但必须给幂等短路

**做法** 批量源码改动不手改，写一次性 Node 脚本、跑完即弃，两个硬要求：① **精确锚点** —— 用「存在且唯一」的锚点串做替换，命中数不等于 1 就报错退出；`scripts/patch-contract-v5-preload.mjs` 的 `replaceOnce(from, to, where)` 就断言这两件事，错误文案可直接 grep：`找不到锚点（${where}）` / `锚点不唯一（${where}）`。② **幂等短路** —— 脚本跑完不删（为了能重跑），但必须让重跑变 no-op。反例真实踩过：**「函数返回之后才 `writeFileSync`」这种写法让重跑变成追加**，同一个文件被写两遍。所以每个 patch 开头加短路，例如 `if (src.includes('appearanceMode')) return src`，或像 v5-preload 直接在 main 里退出：`if (src.includes('webUtils')) { console.log('SKIP preload（已经打过了）'); process.exit(0) }`。

**验证** 首跑有改动日志、`pnpm typecheck` 通过；**二跑**打印 `SKIP ...（已经打过了）`，文件 mtime 与内容 hash 不变。这一步不做，「幂等」就只是口号。

### D4　多子代理并行必须做文件所有权互斥

**现象** 两个子代理并行改同一片代码，最后留下**两份重复 import**，`TS2300 Duplicate identifier ...`，随后 **rolldown 直接把 build 打死**（不是警告，是构建失败）。**根因** 子代理之间**看不到彼此的中间状态**（各自独立上下文），两个都被授权改同一个文件就必然互相覆盖。**修法** 派活时**显式划分文件所有权**：一个文件同一时刻只属于一个执行者；跨文件共享的改动（如契约层）**串行做**，别并行；派活 prompt 里写清「你只许改这几个文件，别的一个字都不许动」。**验证** 合并后 `pnpm typecheck` + `pnpm build` 都过；grep 重复标识符为空（`grep -n "^import" <file> | sort | uniq -d`）。

### D5　子代理有 active 上限（10，按累计算）

**结论** 并行子代理 active 上限是 **10**，而且是**累计**计数 —— 用完只能自己写。**工程含义** 派活按「批」规划，别一轮把预算烧光；剩下自己能干的活（补丁脚本、探针、文档）自己干，别把额度浪费在「一句话就能确认」的小任务上。**验证** 批量派活前先 `list_agents` / `job_list` 看当前占用，规划成 ≤10 的批。

### D6　`backdrop-filter` 复现不了 WinUI「亮度补偿为主」的毛玻璃模型

**现象** 照抄 WinUI 的 XAML 数值（`TintOpacity` 亮 0 / 暗 0.15，`LuminosityOpacity` 0.85–0.96）在 CSS 里做出来**偏实色**、几乎看不出透。**根因** WinUI Acrylic 是「**亮度补偿为主**」的模型（`LuminosityOpacity` 0.85–0.96，观感几乎全靠亮度补偿、色染极轻），而 CSS 的 `backdrop-filter` 只有 `blur()` + `saturate()` 这类**模糊 + 饱和度**调整，**没有亮度补偿**这一环 —— 两者不是同一套算子，数值不能直接搬。**修法** 浮层用 `backdrop-filter: blur(30px) saturate(125%);`（对应 WinUI 源码 `sc_blurRadius=30`、`sc_saturation=1.25`）；想更透就把不透明度降到 **0.75–0.80**，并**必须重测对比度**。这一条的自报不确定性要如实写进报告：`docs/ref-notes.md` 自己把「降到 0.75–0.80」标为**最不确定项之一**且要求按对比度验收流程（§5）重测 —— 所以这里给的是**范围**，不是定值。**验证** 在浅色与深色两套底图上各截一张浮层，量前景文字与背景的对比度是否仍达标；把 0.85 / 0.80 / 0.75 三档做成对比图存档。

### D7　别自己拼 pnpm：复用官方 `operations` 通道

**现象** 自己拼 `pnpm add` 去写 profile，会撞上一串官方才处理得好的问题：装完 `package.json` / `cordis.patch.yml` 不同步、兼容性门禁没跑、失败没回滚、日志拿不到、并发写锁没有。**根因** DSH 有**官方写通道**模块，这些保证都是它提供的；在外面自己拼命令等于把它们全部放弃。**修法** 直接复用：

```
<installRoot>/resources/app/dsh/node_modules/@deepseek-ai/dsh-plugin-manager/lib/types/operations.js
```

（无 `.d.ts` 零类型；有独立 export 子路径 `./operations`。）一次拿到：`reconcile()` 清单对账、兼容性门禁（不兼容则 `exitCode 1` 且**什么都不装**）、快照回滚（`writeFileAtomic` 还原 `package.json` + `pnpm-lock.yaml`）、诊断日志 `<profile>/.plugin-manager/logs/operation-<随机>/pnpm.log`、跨进程写锁 `withFileLock(join(dir, 'package.json'))`。调用要点（`src/main/engine/dshpm.ts:1-25` 头注释成文）：① **`execution: 'service'` 是唯一能拿输出的模式** —— `'cli'` 是 inherit，`child.stdout` 是 `null`，`onOutput` 永不触发，`output` 空；② **`PATH` 必须自己塞进 `options.env`** —— 传 env 会覆盖官方内部的 `scrubbedParentEnv()`，否则 git 依赖和生命周期脚本找不到可执行文件；③ **官方只有 `idleTimeoutMs`（静默超时）没有整体超时** —— 整轮上限自己控制：`AbortController` + `AbortSignal.any([...])` 传 `options.signal`。**验证** 一次完整安装后 `<profile>/.plugin-manager/logs/operation-*/pnpm.log` 存在且有内容；不兼容插件被拒时 `exitCode 1` **且 profile 未被改动**（`deps=16 / bundles=18` 不变，见 D1）。

### D8　清单数据源必须是 `dependencies ∪ bundles`，插件判据只有一个字段

**现象（两个方向都踩过）** ① 只读 `dependencies` 会**漏掉**官方内置包（`@deepseek-ai/dsh-base`、`dsh-web-app`、`dsh-headless` 这些只在 `bundles` 里）；② 拿 `dsh` 字段存在性当判据，会触发 DSH 警告 `warning: <name> declares no dsh.bundle — installed as a plain dependency, not as a profile layer`。**根因** profile 是**两套账**：`package.json` 的 `dependencies`（依赖树，无序）与 `dsh.profile.bundles`（加载层，**有序数组**），另有 `cordis.patch.yml`（顶层数组，patch 层）。「是不是 DSH 插件」的唯一判据是 **`package.json` 里有没有 `dsh.bundle.patch`**，证据在官方 `operations.js` 的 `bundleManifest()`：`return manifest.dsh?.bundle?.patch === undefined ? undefined : manifest`。

**修法** 清单数据源 = `dependencies ∪ bundles`（按包名取并集，顺序信息取自 `bundles` 数组下标）；判插件只认 `dsh.bundle.patch`；依赖 `reconcile()`（同文件 `:96`）三条推论：① 新增只追加末尾；② 自己把包从 `bundles` 摘掉后官方通道**不会**塞回来；③ 从 `dependencies` 移除后 `bundles` 会自动过滤。**验证** 侧栏三个 profile 的账能对上（`docs/_ready1.json`）：`desktop 16 插件 · 18 加载层` / `headless 0 插件 · 2 加载层 未初始化` / `web 7 插件 · 9 加载层` —— **16 vs 18 就是两套账的差**；过滤 tab「全部 16 / 可更新 0 / 已停用 4 / 第三方 16 / 官方内置 6」。

### D9　「当前版本」不能用远端最新版顶替

**现象** 版本选择器里「当前版本」标在了**远端最新版**上，真正已装的旧版被标成「降级」，方向**完全反了**。**根因** `installPreview.resolvedVersion` 是**远端最新版**，不是已装版本。**修法（四条，见 `docs/_log.md` 第七节）**：① 「当前版本」必须查**本地已装** —— `state.plugins` 里 `installed && name === 目标包名` 的 `version`；查不到传 `undefined`，**传 `null` 会被当成「确实没有这个包」**，组件兜底分支就不触发了；② 喂 picker 的 npm 包必须是**包名**而非 profile 里的 spec —— `^0.78.1` 会让 `parseSpec` 判成「只有版本号没有包名」**直接失败**（面板空着）；规则：`sourceKind === 'npm'` 传 `rec.name`，`'git' | 'tarball'` 传原 spec（`github:owner/repo#ref` 才有标签可挑），`link:` / `file:` / `workspace:` 本地目录**不出现**版本列表按钮；③ install 分支原本只统计「新增包」，换版本/降级被报成「安装命令执行成功，但没有检测到新的包（可能本来就装过）」，改成同时收集 `swapped`，摘要三态：`已安装 X` / `版本已替换：X 旧 → 新` / `安装命令跑完了，但这个包当前就已经是这个版本，没有变化`；④ **git 版本列表额度分配** —— 走 `git ls-remote --symref --refs --heads --tags <url>`，注意 **`--refs` 会把 `ref: refs/heads/X	HEAD` 那行一起滤掉**，默认分支要**另补一次** `git ls-remote --symref <url> HEAD`；上限**按类别各算**（80 tag + 80 branch）—— 合并计数会把 `dsh-market` 的 **28 个分支**全挤没（它有 **195 个 tag**），而挑分支正是主用途。**验证** picker 打开时「当前」贴在**本地已装**那一行；升降级方向正确；`dsh-market` 的版本列表里分支与 tag 都在（各 80 上限）。

### D10　三个「字段类型与文案」类静默坑

**现象 → 根因 → 修法** ① **`OpResult.log` 是 `string`，不是 `OpLogLine[]`** —— 当数组遍历会得到一堆单字符或直接崩；流式日志走 **`EV.op:log` 事件**。② **`AppSettings.extraPnpmArgs` 是 `string`，不是 `string[]`** —— 按数组渲染会每个字符一个 chip。③ **tab 文案带计数不能用 `===` 判** —— 实际文案是「已安装 22」这种带计数串，必须 `startsWith('已安装')`。根因都在跨进程边界（IPC）上：类型信息在运行时全丢，TS 写错编译期未必报、运行期静默错。**验证** CDP 里直接读真实值确认类型（`typeof (await window.dsh.<op>()).log === 'string'`）；tab 选择改 `startsWith` 后能稳定命中（多次跑不 flake）。

## 5.6 E 组：工具链、网络与外部依赖坑

### E1　`curl` 走本机代理恒返回 `000`

**现象** 设置 `HTTP_PROXY` / `HTTPS_PROXY=http://127.0.0.1:65535` 后，`curl` **恒定返回 `000`**（连不上、也没有 HTTP 状态码）。**根因** 该端口不是可用代理（代理不通/协议不符）。反直觉点：**同一个 `127.0.0.1:65535` 在别处是能用的**（Electron `net.fetch` 走系统代理、pnpm/git 配代理可通），所以「代理地址有值」≠「curl 能用它」—— `curl` 对代理协议的判定更严格。**修法** 抓取链路**弃用 `curl`**，改用 `web_fetch`（或 `read_page`）；需要给 git 走代理时在 git 的配置/环境里配（不配代理时 `git ls-remote` 到 github.com 会超时：`Failed to connect to github.com port 443 after 21063 ms`）。**验证** `web_fetch` 能拿到目标页正文；`git ls-remote --symref --refs --heads --tags <url>` 能返回 tag/分支列表。

### E2　`read_page`（Firecrawl 云端渲染）keyless 额度会耗尽 → HTTP 429

**现象** 前期能用的 `read_page` 后期全部失败：`HTTP 429，retry_after ≈ 86077–86211s`（另有一次 `m3.material.io/styles/color/dynamic` → Firecrawl 429，`retry_after ≈86211s`）。**根因** keyless 模式的共享额度被耗尽，`retry_after` 是**小时级**（≈24 小时），等于当天这条路直接没了。**修法** 切到 `web_fetch`；对 Apple HIG 这类有静态源的站点，直接抓官方 `<page>.md` 静态源（比渲染 JS 更稳）。**验证** 换链路后成功拿到正文；把失败清单与 429 原文记进 `docs/ref-notes.md` §6（`docs/ref-notes.md:590-641`）—— 这步不能省，否则下次还会重走。

### E3　`web_fetch` 会因 content-type 不支持而拒

**现象** `unsupported content type "application/octet-stream"`（Apple 支持页 `.../reduce-motion` 就是这一类）。**根因** `web_fetch` 只解码它认识的文本类型；服务器把内容按二进制流返回（或没给对 content-type），工具就直接拒。**修法** 找同页的静态/替代源（官方 `.md` 版本、raw 文件），或用 `read_page` 走渲染。**验证** 同一内容有第二种来源能取到且内容一致。

### E4　`pwsh Invoke-WebRequest` 抓 `raw.githubusercontent.com` 会挂起

**现象** 抓 `raw.githubusercontent.com` **挂起 >120s**（最后手动 kill）。**根因未定位** —— `Invoke-WebRequest` 会自动走系统代理并有自己的超时策略，在本机这个代理环境下它既不返回也不报错；具体是代理协商还是 IE 引擎代理设置的哪个环节未查明，但现象 100% 复现。**修法** **不用 PowerShell 抓网页**：需要抓就交给子代理 / `web_fetch` / `fetch`；要拿 GitHub 上的 `package.json` 用 `raw.githubusercontent.com/<owner>/<repo>/<ref>/package.json`。**验证** 换成子代理 + `web_fetch` 后同一 URL 秒级返回 200。

### E5　`api.github.com` 匿名 60 次/小时，一撞就打光

**现象** 批量查插件元数据时 403：`API rate limit exceeded for 203.10.99.66`。**根因** 未认证额度 **60 次/小时**且按**出口 IP** 计 —— 本机出口已被打光，等一小时也不会立刻好；而 8281 条目录的规模，任何按条调 api 的设计在第一秒就死了。**修法**（`src/main/engine/net.ts:477-482` 注释原文就是这个决定：**为什么不只靠 api.github.com：未认证的 60 次/小时一撞就打光（实测就是 403），而 raw 域名基本不限流。**）：读远端 `package.json` → `raw.githubusercontent.com/<owner>/<repo>/<ref>/package.json`（实测 200，基本不限流）；列 tag/分支/默认分支 → **本机** `git ls-remote --symref --refs --heads --tags <url>`（无限额）；`api.github.com` 只用来补 `description` 与默认分支这两个「顺带」字段。**验证** 同批操作不再出现 403；raw 返回 200；`git ls-remote` 能列出 `dsh-market` 的 195 个 tag 与 28 个分支。

### E6　pnpm 11 的三个「安装层」钉子（A3 讲的是拦构建脚本，这里是另外三个）

**E6.1　`ERR_PNPM_GIT_DEP_PREPARE_NOT_ALLOWED`** —— 现象：GitHub 来源的插件装不上，pnpm 报该错误且**什么都不装就退出**（不是部分成功）。根因：pnpm 11 默认不跑 git 依赖的 `prepare`/`build` 生命周期脚本，而插件仓库靠 `prepare` 编译产物。修法：往 `<profile>/pnpm-workspace.yaml` 的 `allowBuilds` 写**精确 key**（必须带完整 codeload URL，不能只写包名），实测两条：
```yaml
'dshmarket@https://codeload.github.com/dsh-market/dsh-market/tar.gz/c01a967a...': true
dshmarket@1.73.8: true
```
写入后 prepare 真跑了，日志可见 `Build complete in 110ms`。验证：日志出现 `Build complete in 110ms`，插件真的出现在 bundles 里。

**E6.2　供应链冷却把 `@latest` 悄悄压回旧版** —— 现象：`dsh-context` 远端明明有 `0.79.0`，装完却是 `0.78.2`，「可更新」标记**永远亮着**。根因：pnpm 的 `minimumReleaseAge`（供应链冷却）—— 太新的版本默认不装，**不报错、不提示**，只是安静地给你旧版。失败尝试：❌ 把 argv 从 `@latest` 改成钉 `rec.latestVersion` 无效，因为那批 records 刚读盘时 `latestVersion` 一律是 `null`，钉了个 `null`。修法：✅ **先补一次远端查询拿真实版本号，再钉精确版本**；判断依据是 pnpm 会打印 `Added 1 entry to minimumReleaseAgeExclude in pnpm-workspace.yaml ...`，说明钉精确版本就是正解（pnpm 自己把它加进冷却豁免）。验证：装完版本号 = 远端最新版，「可更新」标记熄灭。

**E6.3　`--reporter=append-only` 的位置** —— 现象：流式日志变成**覆盖式乱码**（一屏一行原地刷新，历史全丢）。根因：`--reporter` 是**全局选项**，必须插在**第一个非选项参数之前**（即子命令之前）：`pnpm --reporter=append-only add ...` 而不是 `pnpm add ... --reporter=append-only`。修法：拼 argv 时把 reporter 插到子命令前，且**调用方已自带 `--reporter` 时不要重复加**（重复会直接报参数错）。验证：`operation-*/pnpm.log` 是**完整的追加式**文本，包含全部行而不是最后一屏。

### E7　`raw` 路径拼接要分段编码，但分支名里的 `/` 不能编

**现象** 按「仓库 + 分支 + 子路径」拼 raw URL 时，路径里带特殊字符（`#`、空格）会 404；而带 `/` 的**分支名**（`feature/xxx`）如果整体 `encodeURIComponent` 也会 404。**根因** raw 的 URL 结构是 `/{owner}/{repo}/{ref}/{path}`，`ref` 里合法地包含 `/`；URL 语义里 `/` 是**路径分隔符**，编码成 `%2F` 之后 GitHub 不再按分支名解析。**修法** 按 `/` **分段**做 `encodeURIComponent`，但**分支名里的 `/` 保留成路径分隔符**（不编码）。**验证** 两种输入都过：无斜杠分支名 + 带斜杠分支名各取一次 `package.json`，均返回 200。

## 5.7 如果重来一次，我会先做什么

下面的顺序本身就值钱 —— 每一条当时都是**踩到才想到**的。

1. **先确认 CSP，再谈图标。** 碰任何图标解析逻辑之前，先做 `probe-icon-sanity.js` 那三件事（读 CSP 原文 / `<img>` 试 URL / `fetch` 试同一 URL）。三行探针省掉半天推理 —— B4 里四个假设就靠这一刀切开。纪律：**改任何「资源加载不出来」的问题前，先把 CSP 抄下来。**
2. **先量 DOM 增长，再谈性能。** 打开列表 → 连续滚到底 12 次 → 打印 `cards / domNodes / scrollHeight` 三条曲线。只要 `scrollHeight` 在**线性无上限**增长，性能问题就已经定案在「虚拟化」上，不必再猜 `useMemo` / `React.memo` / 图标解码。C1 的数字（9529 DOM、30836 scrollHeight）如果一开始就量了，就不会先去做分页式「再看 48 个」。
3. **先做 DPI awareness 再谈截图。** 坐标系错误与前端布局 bug 的**产物长得一模一样**（左上裁一块 / 右半黑）。所以第一步是让坐标系正确：`SetProcessDpiAwarenessContext(-4)` + `DWMWA_EXTENDED_FRAME_BOUNDS` + `PW_RENDERFULLCONTENT`，再开始看图。A4 的误判本来是零成本的。
4. **契约层一次性设计完整再动手。** `src/shared/` 是**三处同步**的代价中心（D2）。先花时间把 types / ipc / preload / main 的**完整形状**定下来（包括错误语义：本项目统一「永不抛异常，折成 `{ok:false, status, data:null, error}`」，见 `net.ts:2-6`），再开始写；否则每次小改都要四处对齐，而漏 preload 那侧是**静默失效**。
5. **先写探针，再写功能。** `scripts/` 这套（`cdp-eval.mjs` + `probe-*.js`）在项目后半段救了大量时间。如果一开始就当基础设施（CDP 求值 + 截图 + JSON 落盘 + 阈值判定），每个功能都能「带数字收工」，而不是「看起来能用」。
6. **先跑通启动链的三个前置条件，再抱怨「没反应」。** 清 `ELECTRON_RUN_AS_NODE` → kill 后等 5 秒 → 窗口抬到前台。这三条覆盖了「进程在但不显示」「双击没反应」「截图是黑的」三类症状的绝大部分。先建立**可观测的干净起点**，再谈复现。
7. **先确认写通道（官方 `operations`），再写任何写 profile 的代码。** 自己拼 pnpm 的代价是契约、回滚、日志、锁全丢（D7）。这个决定应该在第一天做。
8. **先把「哪些字段是 string」查清，再写 UI。** `OpResult.log`、`AppSettings.extraPnpmArgs`、tab 文案带计数（D10）—— 三条都是跨进程类型的静默坑，代价只是「先读一遍官方类型 / 先 dump 一次真实值」。

## 5.9 一句话收尾
