## A.1 `docs/design-brief.md` —— 甲方侧的约束蒸馏

### A.2.1 六个硬答案（逐条标来源）

**① Mica 是 opaque；Acrylic 只用于临时浮层；真实 tint 几乎全靠亮度补偿、色染极轻**

- 来源：`docs/ref-notes.md` §1.1（MS Learn · Mica 材质页）、§1.4–§1.5（MS Learn · Acrylic 材质页 / AcrylicBrush 类）、§1.23（WinUI 3 主题资源源码实测，`Common_themeresources_any.xaml`）、§1.28（WinUI 源码 `AcrylicBrush.h`）。
- Mica 的原话是 "an opaque, dynamic material"，且只采样壁纸一次 → **它是不透明的，不是毛玻璃**。长期窗口底材质用它。
- Acrylic 的原话是 "Acrylic is used only for transient, light-dismiss surfaces such as flyouts and context menus." → **临时浮层材质**。竖排侧栏官方明确建议不要用（"For vertical panes or surfaces that help section off content of your app, we recommend you use an opaque background instead of acrylic."）。
- **一手源码 tint 真值**：暗色 `TintColor #2C2C2C / TintOpacity 0.15 / TintLuminosityOpacity 0.96`；亮色 `#FCFCFC / 0.0 / 0.85`；Base 变体暗 `0.5 / 0.96`、亮 `0.0 / 0.9`。
  **读法**：`TintOpacity` 只有 0.15，而 `TintLuminosityOpacity` 高到 0.85–0.96 —— 观感几乎全靠**亮度补偿**，色染极轻。社区流传的 `TintOpacity 0.5 / TintLuminosityOpacity 0.8` 与官方源码对不上。
- 层级归属：base 层放材质，content 层用**低 alpha 纯色**（`LayerFillColorDefault` 暗 30% 白 / 亮 50% 白），不是再叠一层材质。

**② 噪点是官方固定层，一手真值 `sc_noiseOpacity = 0.02f`，贴图 256×256 PNG**

- 来源：`docs/ref-notes.md` §1.28（WinUI 源码 `AcrylicBrush.h` 实现常量）、§1.4（MS Acrylic 页）。
- 官方配方顺序：`translucency → blur → exclusion blend → color/tint → noise`。AcrylicBrush 文档原话 "uses multiple effects including blur and a noise texture"。
- **一手真值**：`sc_blurRadius = 30.0f`、`sc_noiseOpacity = 0.02f`（**2%**）、`sc_exclusionColor = #1AFFFFFF`（≈10.2% 白）、`sc_saturation = 1.25f`；噪点贴图 **256×256 PNG**。
- 跨来源一致（§2 共识第 ⑨ 条）：MS / Apple / Fluent 2 三方都说噪点强度极小（2% 量级）。

**③ 边框 1px 是硬值；官方 alpha 暗 `#12FFFFFF` / 亮 `#0F000000`；内高光是竖直渐变 + `ScaleY=-1`**

- 来源：`docs/ref-notes.md` §1.7（MS Layering & elevation）、§1.23（WinUI 3 主题资源源码）、§1.30（WCAG）。
- Win11 所有 elevation 档的 stroke width 都是 **1px**，「1px 描边」不是审美选择而是官方硬值。
- **官方 alpha 真值**：默认描边 暗 `#12FFFFFF`（白 7%）⇄ 亮 `#0F000000`（黑 6%）；次级 白 9.4% ⇄ 黑 16%；卡片描边 黑 10% ⇄ 6%；分隔线 白 8% ⇄ 6%；飞层描边 黑 20%。
- **1px 内高光不是我们发明的**：`ControlElevationBorderBrush` 本来就是一个竖直 `LinearGradientBrush`（`0,0 → 0,3`，stop 0.33 → 较亮、1.0 → 较暗），并配 `ScaleY="-1"` 保证**顶部恒亮**。

**④ WCAG 4.5:1 / 3:1 / 7:1 不可四舍五入；非文字元素 3:1（1.4.11）；Apple clear 变体在亮底加 35% 暗化层**

- 来源：`docs/ref-notes.md` §1.12（W3C WCAG 2.2 SC 1.4.3）、§1.30（1.4.6 / 1.4.11 / 2.3.3）、§1.9（MS 无障碍文本要求）、§1.13（Apple HIG Materials）、§1.19（Apple HIG Accessibility）。
- 正文 **≥4.5:1**；大字号（**≥24px 常规 或 ≥18.5px 粗体**）**≥3:1**；AAA **7:1**。且**不可四舍五入**，官方原话 "4.499:1 would not meet the 4.5:1 threshold"。
- Apple 同值：≤17pt 用 4.5:1、≥18pt 用 3:1、**加粗任意字号 3:1**。
- **非文字元素（1px 描边、图标、状态点）另有一条 ≥3:1 的线**（WCAG 1.4.11，原话 "2.999:1 would not meet the 3:1 threshold"，inactive 组件豁免）。这一条直接决定了侧栏收起态图标按钮的描边与状态点颜色。
- 毛玻璃保底三招：让背景受控（纯色/单色）、blur 提到 40px+、提供「降低透明度」开关换纯色。
- **Apple clear 变体在亮底上另加 35% 暗化层**（不加的话官方原话是 "legibility gets noticeably worse"）。

**⑤ Windows 时长给足毫秒；Apple 一个毫秒都不给**

- 来源：`docs/ref-notes.md` §1.24（MS Timing and easing）、§1.25（MS Motion in Windows）、§1.26（MS motion-in-practice）、§1.18（Apple HIG Motion）。
- **Windows**：面板滑入 **300ms + Default Decelerate**（`cubic-bezier(0,0,0,1)`）；滑出/淡出 **150ms + Default Accelerate**（`cubic-bezier(1,0,1,1)`）；纯淡入淡出 **83ms（Linear）**。签名动效表进入 **167/250/333ms**，退出固定 **167ms**（原文 "(ALWAYS combine with fade out)"）；token `ControlFaster / Fast / Normal` = **83 / 167 / 250ms**。
- **Apple**：只有 "Keep durations short"、30–60fps、禁用 ~0.2 Hz 持续振荡 —— **没有任何毫秒数**（§6「未找到」清单第 ④ 项确认这是空白）。
- reduce motion：Windows 关 `Animation effects` / 读 `UISettings.AnimationsEnabled`；Apple 用 dissolve 替代 zoom/slide，并**去掉 blur 的进出场动画**。
- 落地结论（§3 冲突第 ④ 条）：本项目**直接采用 Windows 的 300/150ms 2:1 不对称**，Apple 侧只能定性、不折算假数值。

**⑥ Liquid Glass 高光「从指尖底下起光」；SwiftUI `interactive(_:)` 是显式开关**

- 来源：`docs/ref-notes.md` §1.17（Apple WWDC25 Session 219 逐字稿，问题 6 的一手来源）、§1.22（SwiftUI · Applying Liquid Glass to custom views）、§1.18（Apple HIG Motion）。
- 机制：环境光源照到材质几何（"highlights that respond to geometry"），交互时「**从指尖底下起光**」并扩散到邻近玻璃元素；设备运动只 "in some cases" 参与。
- **官方没有公开指针坐标映射或跟随延迟参数**（§6「未找到」清单第 ⑤ 项）。
- **工程级证据**：SwiftUI 的 `interactive(_:)` 是一个**显式开关**，不打开就不响应触碰与指针 → 「高光不该一直动」有 API 级背书。Motion HIG 亦写明 "Don't add motion for the sake of adding motion."，且触摸响应强于触控板。
- 落地结论：本项目把高光做成**一次性 320ms 事件**（`--gl-hl-dur`），而不是跟随指针的持续效果。

### A.2.2 §2 跨来源共识（14 条）与 §3 冲突点（8 条）

**共识里对实现影响最大的四条**：

1. **材质 = 分层不是装饰**。MS 明确禁止 "apply backdrop material more than once"，也禁止把材质贴到 UI 元素上。
2. **毛玻璃只适合临时、可关闭、面积小的表面**。MS："Don't put desktop acrylic on large background surfaces."；NN/g："glassmorphism is best when utilized sparingly to create an illusion of depth."
3. **必须给用户关闭透明度的开关**。系统「设置 > 个性化 > 颜色」可关，Battery Saver 会自动关；Fluent 2 另要求 "no motion" 开关。
4. **不要在材质上放大面积彩色文字**：MS 原话 "Don't place accent-colored text over acrylic surfaces."

**最值得注意的冲突（§3 第 ⑥ 条）**：侧边栏**能不能**让内容透出来 —— MS 要竖栏不透明，Apple 却要 "Extend visually rich content beneath the sidebar."，并且大元素自动 "more opaque"。本项目的落法是取中间路线：**侧栏用不透明底、浮层用材质**；若将来真做「内容延伸到侧栏下」，必须同时把侧栏底色提到接近不透明。

**§3 第 ⑦ 条（拆开关的依据）**：关闭透明度之后两家行为并不一样 —— MS 退为系统纯色；**Apple 的 Reduce Transparency 只是更 "frostier"，变纯黑/白加对比描边的是 Increase Contrast**。所以本项目把「降低透明度」和「提高对比度」做成两个独立开关（`src/shared/types.ts:301` / `:303`）。

**§3 第 ⑧ 条（描边可以多亮）**：纯装饰分隔线 6–10% alpha 可以照抄官方；但**控件边界、输入框边界必须 ≥3:1**，不能只靠 6% alpha。

### A.2.4 §5 可读性红线与 §5.2 禁令清单

**§5.3 保底对比度表**：正文/小字号 ≥4.5:1（不可四舍五入）｜大字号 ≥3:1｜非文字元素 ≥3:1｜AAA ≥7:1｜失活 UI 内文字、纯装饰、logo 无要求｜毛玻璃压明亮富媒体 → 加 35% 暗化层。

**§5.3 保底做法优先级**（顺序不能乱）：让毛玻璃只出现在背景可控处 → 加一层对比保证层 → 不依赖单一测量点（逐点测）→ 提供降低透明度开关 → **不要把高对比度模式当兜底**（原话 "Do not treat high-contrast mode as the primary mitigation for low readability."）→ 全做不到则保证 WCAG-compliant。

**§5.2「什么时候不该用毛玻璃」合成清单（11 条）**：①常驻竖排侧栏 / 分隔内容面板用不透明 ②大面积背景表面 ③两块 acrylic 并排（会出现 "undesirable visible seam"）④同应用叠两层材质 ⑤毛玻璃上放强调色文字/超链接 ⑥glass on glass ⑦材质用在内容层（"Don't use Liquid Glass in the content layer."）⑧thin/ultraThin 上放四级文字 —— 侧栏这类大量文字的组件**必须用 regular 变体** ⑨clear 变体用在非富媒体背景 ⑩背景不可控且底部是视频/照片/动画 ⑪装饰性到处用。

## A.3 `docs/design-v3.md` —— 设计主管的完整设计稿（1223 行 / 63 节）

### A.3.1 §0 设计立场（`docs/design-v3.md:10-32`）

**产品与受众**（`:12`）：本地插件管理工具，受众一个人，第一屏要回答「让我在 3 秒内看清…」。

**记忆点 = 缝隙刻度 gap strip**（`:14-16`）：侧栏状态区里一条 4px 宽、按 `bundles` 下标排列的刻度带；展开态横向 18px 高一条，收起态竖过来变成 8px 宽的柱（**42 段 × 1.5px**）。语义是「装了 ≠ 加载了」：在 `bundles` 里的是实心刻度，被移出的是**下沉 3px 的空心缺口**，hover 出「`@scope/pkg` · bundles 无此下标」，点击缺口跳到「已停用」筛选。

**拒绝的两件事**（`:18-21`）：①不做「每项各闪一下」的选中反馈 → 改**玻璃滑块**（原话：「一块会移动的玻璃表达的是选择是一个位置」）②不做面板打开时整体 fade-and-slide-up —— 编排只留给「壁纸刚切换 / 自动适配完成」，侧栏展开收起只做宽度 + 内容交叉淡化 **140ms、不位移**。

**三条硬规则**（`:25-29`）：

1. **数据永远不落在模糊层上** —— 数据先坐 `--mt-bed-tint` 衬底（深 0.72 / 浅 0.80）+ 1px 描边 + 8px 局部 blur；文字用**纯色** `--p-mist`/`--p-ink` 而不是 alpha 文字色；正文 ≥4.5:1，数字与版本 **≥7:1**。
2. **模糊预算是分配的不是铺开的** —— 面板中央的 blur 只作用在衬底之外那一圈；融合感由**外边缘 24px 折射环 + 面板外 10px 留白**提供。
3. **壁纸永远比内容弱一档** —— 遮罩下限深 ≥0.28 / 浅 ≥0.16，判定为复杂主体图案时上限 +0.10。

`docs/design-v3.md:31` 的金句：「不是『玻璃上放数据』，是『玻璃柜里放仪器』。」**这一句是后来 C.4 那一轮返工的依据。**

**核心张力**：材质是壳，数据是硬的。壳可以换、可以软、可以让；数据的位置、对比度、可读性不让。

### A.3.2 §1 Token 系统（`docs/design-v3.md:35-330`）

**§1.1 色板**（`:39-73`，深 `:43-50` / 浅 `:54-61`）：核心六色 `--p-ink` / `--p-slate` / `--p-mist` / `--p-brand` / `--p-aurora` / `--p-ember`。**品牌色白名单只此六处**（`:63-69`）：①当前选中导航项文字/图标（滑块到达后 60ms 后）②玻璃滑块内部折射 alpha ≤0.10 ③`:focus-visible` 焦点环（**2px，offset 1px**）④主操作按钮实底 `.btn--primary` 与进度条填充 ⑤状态点「运行中/同步中」两态 ⑥链接型操作文本。`:71` 明禁：正文用品牌色、图标默认色、全局边框、分区标题、当渐变装饰铺大面。语义色 `:73`：`--danger #F2645E`(深)/`#C0392F`(浅)、`--warn #E0A45C`/`#A96A18`、`--ok #4FD08E`/`#1A7F4B`；**六态状态点的颜色全部来自这三族 + 品牌色，不新增第五种色相**。

**§1.2 字体**（`:75-104`）：三套 `--font-ui` / `--font-num` / `--font-ui-display`（**仅 ≥17px 使用**）；不引 web font；`Cascadia Mono` 不能假定存在故首选 `Consolas`；所有数字强制 `font-variant-numeric: tabular-nums` + `font-feature-settings:"tnum" 1,"zero" 1`。**等宽白名单**只给机器字符串（semver、`github:owner/repo`、路径、hash、`bundles` 下标、毫秒数、目录条数），人类数值（`42 个插件`）用 UI 字体 + tabular-nums。字号阶梯 `:93-101` 共八档，@1440 实测 10.9 / 12.2 / 13.3 / 13.9 / 15.4 / 20.0 / 24.1。行长上限 `:103`：正文 `max-inline-size:72ch`、设置面板说明 `62ch`、错误详情 `76ch`；**禁止任何 ≥0.06em 的字距**，只有 caption 允许 `+0.01em`。

**§1.3 间距、圆角、层级**（`:106-166`）：侧栏节奏 `:119-131`；圆角 `:134-144` 用 `r ≈ min(h × 0.28, 22px)` 推七档并给了「为什么是这个值」；z 刻度 `:148-162` —— **滑块 11 必须低于内容 12，面板外缘折射环 14 高于内容**（因为它只画在边缘 24px 内）。

**§1.4 版式概念（ASCII 线框）**（`:168-258`）：`:258` 是写死的对齐规则 —— 面板内左边缘对齐 `--sb-pad-x`(12)；数字右边缘对齐内右 12px；图标固定 16px 列，标签起点 = 图标列起点 + 16 + 10；分组标题与导航项文字同起点（**不做缩进层级**）；**宽度切换时图标列中心线保持同一 x**（展开 22+8=30，收起 32，差 2px 用内边距补偿）。

**§1.5 材质 token（四层）**（`:260-319`）：L0 背景 / L1 内容（面板 + 衬底）/ L2 高光 / L3 阴影，**透明度各不相同**。`:313` 四层 alpha 汇总：深色 **L0 0.34 / L1 0.52 / L1′ 0.72 / L2 峰值 0.14 / L3 0.62**；浅色 **0.16 / 0.46 / 0.80 / 0.30 / 0.28**。`:315` 另给了一条**「假玻璃」预合成分支**（壁纸降采样 64px、高斯模糊 12px、按 `--gl-panel-alpha` 混色成静态 data URI），触发条件 = `prefers-reduced-transparency: reduce` / GPU 评分低于阈值 / 浮层数 > 2；代价是滚动时与壁纸不同步。`:317-319` 高光纪律：只允许六个事件（`hover-in` / 选中变化 / 面板刚打开 / 壁纸刚切换 / 主题变化 / 操作成功），一次性 transition，**不允许任何 `animation-iteration-count: infinite` 的高光、扫光、沿边框移动**。

**§1.6 高层原则六条**（`:321-328`）：①数字是硬的（≥0.72 alpha 衬底，数字与版本 ≥7:1）②高光是事件不是状态（320ms 峰值 0.14 必须衰减到 0）③半径随高度递减 ④一屏只有一个主角（只有玻璃滑块会明显动）⑤壁纸永远弱于内容 ⑥键盘与高对比是硬地板。

### A.3.3 §2 动效 token（`docs/design-v3.md:332-418`）

### A.3.6 §5 壁纸自动适配算法（`docs/design-v3.md:857-1103`）

目标（`:859`）：一张壁纸进来，输出 §3.22 那 17 个字段里与材质有关的**全部**参数，并给出侧栏位置建议与「文字安全区」图；全流程在 Worker 里跑，主线程阻塞 ≤4ms，总目标 <40ms（1440×900 基准机）。

- **§5.1 输入与预处理**（`:861-878`）：`AdaptInput = { bitmap, targetSide, panelRect, viewport, current }`。三步预处理：①降采样 **256×256**（`OffscreenCanvas` + `imageSmoothingQuality:'high'`，按 `object-fit: cover` 的裁切规则先裁再缩）②再生成 **64×64**（主色聚类与连通性）与 **16×16**（全局明暗与位置建议）③转两个平面：`Y`（`Y = 0.2126R' + 0.7152G' + 0.0722B'`，其中 `R' = linear(r/255)`，即 **linear 空间算亮度**，避免 sRGB 下「中灰偏亮」）与 OKLab 的 `L/C/H`。侧栏局部区 `zone`：左 `x∈[0,0.34]`、右 `x∈[0.66,1]`。
- **§5.2 明暗判定**（`:880-896`）：**主判据是 zone 内面积加权均值 `Lzone`**（不是全图分位数）；`Lzone < 0.42 → dark`，`> 0.58 → light`，否则走 **0.42~0.58 中间带不切换**（迟滞带宽 **0.08**）。最终 `L = 0.7·Lzone + 0.3·Lp50`（zone 面积 < 全图 8% 时才用全图兜底）。
- **§5.3 主色提取**（`:898-923`）：不用 median-cut / `quantize()`（都偏大面积背景色）；用 **k-means k=5 在 OKLab 空间**。64×64=4096 点先做弓形采样（每维 8 档 → 512 桶），桶内取均值与权重，按权重降序取 **≤1024 点**；`k-means++` 初始化，5 次迭代或中心位移 <1e-3 停止。Android Monet 两条思想：①**种子选择** `seed = weight ≥ 0.12 且 C ≥ 0.06` 里 `weight × C` 最大者 ②**品牌色生成** `brand = OKLCh(0.62, clamp(seed.C × 0.90, 0.10, 0.22), seed.H + Δh)`，其中 `Δh = ±30°` 取与主题预设品牌色色相更近的符号；若对 `--p-ink` 对比 <3.0:1 → L 提到 0.68，仍不足 → 0.72。理由明写：「与壁纸同色的品牌色会消失在壁纸里，偏移过大又会让玻璃与壁纸脱节，30° 是『看得出是同一片光、但不是一个颜色』」。③辅助色 `= OKLCh(0.58, brand.C×0.75, brand.H − 55°)`，**永不用辅助色做状态色**。
- **§5.4「复杂人物图案」判定**（`:925-941`）：三信号加权 `busy ∈ [0,1]`，**不上人脸模型**。`edge` 边缘密度（256² Sobel，`thr = p95(|∇|)`，`edgeN = clamp((edge−0.01)/0.20, 0, 1)`，~2ms）；`hf` 高频能量比（`hf = Σ(I − blur₄(I))² / ΣI²`，`hfN = clamp(hf/0.06, 0, 1)`，~1.5ms）；`skinBlob` 皮肤团块（YCbCr `Cb∈[77,127] ∧ Cr∈[133,173] ∧ Y∈[0.20,0.90]` 得 `skin`，8×8 网格 4-连通取最大块格数 `blob`，`skinBlob = clamp(skin/0.12,0,1) × clamp((blob−5)/12,0,1)`，~1.5ms）。`busy = 0.50·edgeN + 0.30·hfN + 0.20·skinBlob`，判为复杂主体图案的阈值 **`busy ≥ 0.62`**。不上人脸模型的理由：要回答的是「侧栏压上去会不会遮住主体」，不是「是不是人」。作用：`遮罩 += 0.10×busy`、`面板 opacity += 0.06×busy`、`blur += 8px×busy`、`衬底 alpha = max(主题值, 0.72 + 0.08×busy)`、`壁纸亮度 −8%×busy`。
- **§5.5 文字安全区**（`:943-961`）：面板占位矩形切 **4×4 = 16 块**；每块算局部复杂度 `c_b`、块 Y 均值、对比 `Cr_b = (max+0.05)/(min+0.05)`、`bed_b = clamp(4.5/max(Cr_b,0.5) − 1, 0, 1)`，`c_b > 0.18` 时 `bed_b = max(bed_b, 0.62)`。**不要渲染成 16 个方块** —— 用双线性插值升采样成 **96×96 单通道遮罩**作 CSS `mask-image`，于是衬底跟着壁纸局部强弱变化（平坦暗部几乎不存在，人像高频区变厚）。
- **§5.6 位置建议**（`:963-973`）：三候选带左 0–34% / 中 33–67% / 右 66–100%；`cost(side) = 0.45·macroComplexity + 0.35·(1 − flatness) + 0.20·subjectOverlap`；建议侧 = argmin；`|cost(左) − cost(右)| < 0.04 → 保持当前侧`。主体重心落在建议侧 → `conflict: true` + 预览提示给两个可点动作按钮，**不自动搬家**。
- **§5.7 组装输出**（`:975-994`）：`AdaptOutput` 含 mode / brand / accent / seedHex / sidebarOpacity（夹 [0.30,0.85]）/ blur（夹 [12,40]）/ bedAlpha / bedMask（Uint8Array 96×96）/ veilDark（夹 [0.28,0.60]）/ veilLight（夹 [0.16,0.50]）/ edgeLuma / shadowStrength（`1.00 + 0.15×busy`）/ wallpaperBrightness（`1 − 0.08×busy`）/ suggestedSide / conflict / contrastReport / cost。
- **§5.8 伪代码**（`:997-1084`）：完整可实现的 `adaptWallpaper(input)` 规格（`bowtieSample` / `kmeans(pts,5,5)` / `sobel` / `hfEnergy` / `skinBlobRatio` / `bilinearUpsample` / `subjectCentroid` / `measureContrast`，末尾 `input.bitmap.close()`）。**注意这是算法规格，不是可运行模块**（`:1221` 明确划界）。
- **§5.9 成本与验收**（`:1086-1105`）：降采样+色彩转换 ≤8ms / k-means ≤6ms / Sobel+高频+皮肤 ≤7ms / 安全区 ≤4ms / 合成输出 ≤3ms，**合计 ≤28ms**，目标 40ms 内。**自动适配按钮的三段式编排**（总 ≈520ms + 计算时间）：①读壁纸 0–120ms ②取色 120–280ms ③算安全区 280–440ms（预览格叠 4×4 网格逐块亮起，每块 **30ms**，「**唯一允许的 stagger**，因为它显示的是计算范围」）④参数归位 440–520ms ⑤**结束停在预览态，不自动应用**，底部给变化清单（`遮罩 0.34→0.42` 这种形式，三行以内超出折叠）+ 「应用」/「撤销」两按钮（**「撤销」把滑块走回原位，不是瞬跳**）。

## B.3 后端：`wallpaperProtocol.ts` + `engine/wallpaper.ts` + `engine/themes.ts`

### B.3.1 `src/main/wallpaperProtocol.ts`（164 行）—— 自定义协议 `dshwp://`

**先解决一个真问题**：文件头（`:1-19`）给了三条「为什么不用 `file://`」的理由：①dev 下渲染页是 `http://localhost`，会被拦 ②打包后 CSP 里 `'self'` 对任意目录 `file://` 没有可靠语义 ③壁纸可能几十兆，走 IPC 转 data URL 会撑爆内存与消息体。方案 = 注册 `dshwp://`，主进程按 http 语义返回字节。

三个入口：`dshwp://current`（当前激活壁纸原图）/ `dshwp://thumb/<id>`（缩略图，没有就回退原图）/ `dshwp://files/<rel>`（壁纸目录内相对路径）。

**安全边界（`:17-18` 注释原文）**：「只允许读**壁纸目录内**的文件。所有路径都先 resolve 再校验前缀，越界一律 404 —— 这个协议挂在渲染进程上，必须当成不可信输入处理。」

实现要点：`registerWallpaperScheme()` 在 app ready 前调 `protocol.registerSchemesAsPrivileged([{ scheme, privileges: { standard: true, secure: true, supportFetchAPI: true, stream: true, bypassCSP: false } }])`；`MIME` 表覆盖 png/jpeg/webp/gif/bmp/avif；`respondWithFile()` 做**双层校验**（先 `relative()` 比前缀，再 `realpathSync` 后比前缀**防 symlink 逃逸**），并且**「越界」与「不存在」都返 404、不做区分**，避免把协议变成目录探测面；用 `net.fetch(pathToFileURL(real))` 并补 `content-type` 与 `cache-control: no-cache`；错误返 500 并 `console.warn('[壁纸协议] 读取失败：', …)`。`installWallpaperProtocol()` 按 URL host 分三支；`thumb` 支校验 id 不含 `\0` / `/` / `\`；`files` 支拒绝绝对路径。末尾导出 `currentWallpaperUrl(bust?)` / `thumbUrl(id, bust?)` / `fileUrl(rel, bust?)`，都用 `?v=` 做缓存失效。

> **一处内部不一致**：`WallpaperLayer.tsx` 自己拼了 URL 字面量（`` `dshwp://current/?v=${addedAt}` ``），**没有用主进程导出的 `currentWallpaperUrl`**；而 `WallpaperDrop.tsx:186` / `AppearanceSettings.tsx:336` / `:412` 都用的是字面量 `dshwp://thumb/<id>`。三个 URL 构造函数目前**没有调用方**（未核实是否有其他引用点）。不构成故障（字面量恰好与构造函数同构），但属于「两处各写一遍」的维护风险。

### B.3.2 `src/main/engine/wallpaper.ts`（755 行）—— 壁纸后端

**文件头（`:1-22`）给了三条设计决定，逐条都值得抄下来**：

1. **永远复制用户的原图**。注释原文：「`WallpaperRef.path` 指向我们目录里的副本，绝不引用用户的原位置。用户从『下载』目录选张图，回头一清理，壁纸就变成一片空白；原图还可能在移动硬盘 / U 盘上。副本是我们唯一能保证存在的东西。」
2. **零新依赖**。缩略图用 `nativeImage.createThumbnailFromPath`，取色用 `nativeImage.toBitmap()` 自己算。注释原文：「不引 sharp / jimp / node-vibrant —— 为了几张壁纸多背几十兆原生二进制不值得，而且 Electron 自带的解码器对 webp / gif 的支持跟我们渲染层完全一致。」
3. **自动适配必须能解释自己**。`reasons` 每一条都是给用户看的中文句子。注释原文：「自动适配是个黑箱，调完不给理由，用户只会觉得『它把我的界面搞乱了』。」

**落盘布局**（`:4-7`）：`<userData>/wallpapers/` 下 `index.json`（`{ version, entries: WallpaperRef[] }`）+ `<id>.<ext>` 原图副本 + `thumbs/<id>.png` 缩略图。常量：`INDEX_VERSION = 1`、`OK_EXT = { '.png','.jpg','.jpeg','.webp','.gif','.bmp' }`、`MAX_BYTES = 40 * 1024 * 1024`、`SAMPLE_WIDTH = 160`、`THUMB_W = 480` / `THUMB_H = 300`。`getWallpaperDir()` 导出给别处用。

**索引的健壮性**：`readIndex()` **逐条过滤脏条目**（注释「手改索引 / 半截写入都可能塞进脏条目，逐条过滤比整体放弃强」），坏了就重建空索引并 warn「index.json 读不动，已重建空索引（原图文件没有被删）」；`writeIndex()` 用 `.<pid>.tmp` + `renameSync` **原子写**，rename 失败退 `writeFileSync`，全失败只 warn「本次改动只在内存里生效」；`newId()` = `wp-<base36 时间戳><4 位随机>`（防同毫秒撞 id）。

**取色算法 `analyzeImage(img)`（`:256-371`）** —— 注释（`:246-255`）给了三条实现取舍，每条都是一个具体错误的反面：

- **亮度用分位数而不是均值**：「一张 90% 纯黑 + 10% 纯白的图均值是 0.5，可人眼看到的是『很暗』，均值会把它判成亮色壁纸，进而给出深色文字 —— 直接读不清。」实现里真的算 **`p10` / `p50` / `p90` 三个分位数**（`quantile()` 线性插值），同时也留了 `luma` 均值给「极端色偏」判断用。
- **主色用 5bit 量化直方图，并跳过过暗/过亮/低饱和像素**：「它们数量常常最大，但作为『品牌主色』毫无意义。」实现：`key = ((r>>3)<<10) | ((g>>3)<<5) | (b>>3)` 存 `Map`，**跳过条件 `if (l < 0.06 || l > 0.94 || s < 0.08) continue`**。
- **`detail` 用相邻像素平均绝对差**：「不做边缘检测或连通域分析 —— 我们要的只是一个便宜且稳定的标量，用来回答『背景是不是复杂到会干扰文字』。」横向 + 纵向 `Math.abs(gray[i+1] - gray[i])` 取平均后 `clamp01`。

实现细节里两条踩坑记录：`img.resize({ width: SAMPLE_WIDTH, quality: 'good' })` → `toBitmap()`，注释（`:262`）「`toBitmap()` 给的是 **BGRA**，每像素 4 字节 —— 通道顺序搞错颜色会全反」（读取顺序 `buf[o]=b, buf[o+1]=g, buf[o+2]=r`）；次色要求与主色桶 L1 距离 `> 6`，否则退第二个桶；全灰时主色退 `best95`（最亮处色）、次色退 `best5`（最暗处色）。

返回值 `WallpaperPalette = { dominant, secondary, lightest, darkest, luma, p10, p50, p90, saturation, detail, suggestedMode }`，其中 **`suggestedMode = p50 < 0.42 || luma < 0.45 ? 'dark' : 'light'`**。失败只 warn「[壁纸] 取色失败（壁纸仍然可用，只是没有自动适配依据）」并返 null。

**与 design-v3 §5 的口径差异（必须如实记）**：

| 维度 | design-v3 §5 | `engine/wallpaper.ts` | 差异性质 |
|---|---|---|---|
| 亮度空间 | **linear 空间**（`R' = linear(r/255)`，避免 sRGB 下「中灰偏亮」） | `luma709 = (0.2126r + 0.7152g + 0.0722b) / 255`，**直接在 sRGB 数值上算** | 实质差异：design-v3 的顾虑（中灰偏亮）在实现里没有被处理 |
| 明暗主判据 | **zone 内面积加权均值 `Lzone`**（只看侧栏所在处），全图只做 8% 以下兜底 | 全图 `p50` 与 `luma`，**没有 zone 概念** | 实现更粗：一张「左边很暗、右边很亮」的图会被判成中间调 |
| 中间带防抖 | 0.42~0.58 不切换（迟滞带宽 0.08） | 阈值写死 `p50 < 0.42 \|\| luma < 0.45`，**没有迟滞带** | 缺迟滞 → 换壁纸时判定的稳定性弱于设计稿 |

| 位置建议 | `cost(side)` 三候选带 + 0.04 防抖 + `conflict` | **未实现** | 缺失 |

**这张表是本章最重要的一张**：它说明「自动适配」在实现层是**设计稿的一个简化版**，简化的是**输入侧的分析精度**（色彩空间、聚类、zone、皮肤团块），保留的是**输出侧的完整解释性**。

**`deriveAutoFit(p, current)`（`:390-475`）—— 三条不能违反的规矩**（注释 `:384-388`）：

1. **强调色不能直接用主色**：「一张灰壁纸的主色是灰的，直接拿来当强调色，整个界面的重点色就废了。所以转到 HSL 里往上推饱和度和亮度。」实现 `accent = hslToHex(ah, Math.max(as0, 0.45), Math.min(0.82, Math.max(0.48, al0 + 0.18)))`，`ambient = hslToHex(ah, Math.max(0.08, as0 * 0.6), clamp01(Math.max(0.1, al0 * 0.35)))`。这其实就是 design-v3 §5.3「无主色时用主题预设品牌色 / 对 `--p-ink` 对比不足时提 L」的**穷亲戚版本**。
2. **边框要朝背景的反方向走**：「边框的作用是把面板从壁纸里『拉』出来：暗壁纸配亮边框，亮壁纸配暗边框。跟着背景走就等于把边框藏起来。」实现 `borderBrightness = round2(clamp01(0.16 + (0.5 - p.p50) * 0.4))`，而且**无论走哪支都至少产出一条 reason**。
3. **「跟随系统」才听壁纸**：用户明确选深/浅就以其为准（reason「你手动选的是深色/浅色模式，优先按你的选择走。」）。

派生数值：`busy = p.detail > 0.5`、`veryBusy = p.detail > 0.65`、`extremeTone = Math.abs(p.luma - 0.5)`；`sidebarOpacity` 从 0.62 起（busy +0.12 / veryBusy +0.08 / `+ Math.min(0.1, extremeTone * 0.2)`，上限 0.95）；`sidebarBlur = busy ? Math.round(28 + Math.min(16, (p.detail - 0.5) * 80)) : 28`；`maskDark` 上限 0.8、`maskLight` 上限 0.7；**`enhanceReadability = veryBusy || p.p90 - p.p10 > 0.6`**。

**reasons 的四类中文句子**（每条都是「现象 → 参数 → 后果」三段式）：

- 无调色板：`这张壁纸读不出颜色（可能是格式特殊），沿用当前的默认参数。`
- 复杂度：`背景细节较多（复杂度 X），侧边栏不透明度提到 Y，保证文字压得住。` / `模糊半径加到 Xpx，把背景的琐碎纹理揉开。` / `画面比较花（复杂度 X），遮罩加深到深色 A / 浅色 B，避免图案和人脸干扰阅读。`
- 明暗：`壁纸中位亮度 0.31、平均亮度 0.34，判定为偏暗的图，建议深色模式。`
- 边框：`壁纸偏暗，边框亮度提到 X，让面板从背景里浮出来。` / `壁纸偏亮，边框亮度压到 X，用暗边把面板和背景分开。`
- 强调色：`壁纸本身没什么颜色（饱和度 X），强调色从主色往高饱和方向推了一档，否则整个界面会发灰。` / `强调色取自壁纸主色 X，提亮提饱和后得到 Y。`

**导入 `importOne(filePath)`（`:494-569`）**：一串中文错误文案，每条对应一个真实故障（`没有拿到文件路径` / `这个文件不存在或者已经被移走了` / `拖进来的不是文件（文件夹不能当壁纸）` / `读不到这个文件的信息（可能是权限问题）` / `这个文件是空的` / `这张图有 X MB，超过 40 MB 上限，先压一下再导入` / `不认识 .xxx 这个格式，支持 png / jpg / webp / gif / bmp` / `这个文件打不开，可能不是图片格式` / `复制图片到壁纸目录失败：…`）。
**关键防御**：用 `nativeImage.createFromPath(p).isEmpty()` 判断能不能解码，注释（`:518`）「扩展名骗人（比如 .txt 改名成 .png）在这里被挡住」。
**缩略图异步不阻塞**（注释 `:532`「缩略图失败不算导入失败」）；`ref.thumbPath` 与 `palette` 初值 null —— 注释（`:550-551`）「缩略图是异步生成的，这里几乎必然是 null；UI 拿到 null 就走原图当缩略图。真正的 `thumbPath` 在下一次 `list()` 时才读得到」。`kind: 'image'`（注释「`animated` 是给动态壁纸预留的」）。返回 `{ ok, ref, autoFit: deriveAutoFit(palette, settings.get().appearanceMode), error: null }`；两个入口 `importViaDialog(win)`（取消返 `ok:false, error:'已取消'`）与 `importFromPath(filePath)`。

**列表 / 置顶 / 删除**：**置顶状态单独存 `pinned.json`**，注释（`:613-616`）「置顶是『界面偏好』，壁纸条目是『资产』—— 两者生命周期不同，混在一起以后想换索引结构就得迁移用户数据」。`list()` 把不存在文件的 `path`/`thumbPath` 置 null（注释 `:642`「文件被用户从目录里手动删了 —— 这是有意的，不兜底重建」），按 `Number(b.pinned) - Number(a.pinned)` 稳定排序；`remove(id)` 清原图 + 缩略图 + 索引 + 同 id 所有扩展名遗留副本 + 置顶项；`getRef(id)` 找不到返 null 不抛。

**自动适配出口（`:723-755`）**：`autoFit(id?)` 取 palette 再 `deriveAutoFit`；`applyAutoFit(id?)` 把结果**直接写回** settings（`appearanceMode` / `accent` / `ambient` / `sidebarOpacity` / `sidebarBlur` / `wallpaperAdjust.maskDark` / `wallpaperAdjust.maskLight`），失败只 warn。
**这里是「先预览后确认」的缺口所在**：design-v3 §5.9 第五步明确要求「结束停在**预览态**（不自动应用），底部给变化清单 + 『应用』/『撤销』两按钮」。实现里 `AppearanceSettings.tsx:190-202` 的注释直说了取舍：「`apply=true`：按钮的意义就是把算出来的值真的落到设置上，只算不写等于没点」。也就是说**自动适配按钮是「一键生效」而不是「先预览」**。拖拽导入那条路（`WallpaperDrop.tsx`）走了完整预览，两条路的体验不一致。见 [D.1](#d1-纲领十四条--落地位置--证据)。

**`ThemeSpec` 字段实测 19 个**（`types.ts:686-712`）：`id` / `name` / `builtin` / `description` / `wallpaperId` / `mode` / `accent` / `accent2` / `ambient` / `sidebarOpacity` / `sidebarBlur` / `sidebarRadius` / `maskDark` / `maskLight` / `borderBrightness` / `shadowStrength` / `motionLevel` / `sidebarWidth` / `sidebarExpanded`（另有 `createdAt` / `updatedAt` 两个元字段）。design-v3 §3.22 说的是 17 个字段，实现是 19 个（多出 `id` / `name` / `description` 这类身份字段，性质不同）。

**`apply(id)`（`:177-200`）**：只覆盖外观字段（注释 `:175`「主题不是『设置快照』，不能顺手把 `registry` / 代理那些也改了」），写回 `activeThemeId` / `appearanceMode` / `accent` / `ambient` / `sidebarOpacity` / `sidebarBlur` / `sidebarRadius` / `sidebarWidth` / `sidebarExpanded` / `motionLevel` / `wallpaperAdjust.maskDark` / `wallpaperAdjust.maskLight`。
**缺口**：`accent2` / `borderBrightness` / `shadowStrength` 三个字段**在 `apply()` 里没有被写回**。也就是说用户在主题卡上看到三个色板方块（`AppearanceSettings.tsx:632-636` 渲染 `accent`/`accent2`/`ambient`），但 `accent2` 应用后不会生效到界面。找不到主题时 warn「[主题] 找不到主题 X，保持当前设置不变」并原样返回。

**生命周期**：`newThemeId(name)`（slug + 3 位随机 base36，前缀 `custom-`）；`save()` 带已存在 id → 更新并保 `createdAt`，不带 id → 以当前设置为底新建；`remove(id)` 内置返 false，删的正好是激活主题时把 `activeThemeId` 退回 `FALLBACK_ID`（注释 `:274`「否则界面会停在一套不存在的参数上」）。`exportTheme(win, id)` 写 `{ format, version: 1, exportedAt, theme: {...t, builtin: false}, wallpaperAdjust }`；`importTheme(text)` 校验 `format` 字段与 `theme` 存在，**导入的主题永远当自定义**（id 重了就换新，绝不覆盖内置）。`sanitizeFileName` 换 `[\\/:*?"<>|]` 为 `_` 并截 60。

1. **自动适配按钮是「一键生效」不是「先预览」**（`:190-202`，注释已解释取舍）→ 与 `WallpaperDrop` 的两段式体验不一致，也与 design-v3 §5.9 第五步不一致。
2. **「位置」只有比例偏移，没有 9 宫格与 px 输入**。
3. **`borderBrightness` 在 UI 里不可调**，只能由自动适配写入。

### B.4.6 `useDshStatus.ts`（69 行）

**职责**：订阅 DSH 进程状态的**唯一一处实现**。文件头（`:1-6`）给了理由：「抽出来是因为侧栏要同时用两处：状态卡（点 + 『N 进程』）和 `DshControl`（启停按钮）。两边各自订阅会挂两个 IPC 监听、也会出现『点已变、文字还没变』的错帧。」

接口：`DshStatusView = { status: DshStatus | null; phase: 'loading' | 'ready' | 'error'; error: string | null; reload: () => Promise<void>; push: (s: DshStatus) => void }`。`push` 的注释（`:19`）「启停操作拿到新状态后直接推进来，不用等下一次轮询」。
`useEffect` 里先 `reload()` 拉一次快照，再 `api().onDshStatus()` 订阅推送；卸载时 `off()`，注释（`:63`）「卸载时退订，不然切来切去会叠一堆监听」；用 `let alive = true` 防已卸载后 `setState`。

**对应纲领哪一条**：这是纲领 §7「状态点六态」里「在线 / 运行中 / 加载中 / 失败 / 离线」的**数据源**。它提供的 `phase` 三态（`loading` / `ready` / `error`）与 `status.running` 布尔组合出四态，正是 `SidebarShell.tsx:264-271` 那个 `dotClass` 的来源；也正因为它只有四态，`--online` / `--ok` 两个 CSS 类没有触发路径（见 B.2.5）。

## C.2 第一轮：布局坏（分组标题被当整组容器尺寸；导航区不可滚动会和状态卡叠上）

**证据**：`glass.css:1188-1230` 的注释块，标题是「布局修正（第一轮实机截屏发现）」。注释原文：

> 「1) `.sb__group` 早先被写成『22px 高的一行、flex row』—— 那是把分组标题当成整组的容器尺寸了。实际结构是『标题 + 若干项』的竖排容器，必须回到 block 流。2) 三个分组十项加起来超出面板可用高度，导航区必须可滚动，否则它会和底部状态卡叠在一起（不是被挤下去，是直接压上去）。」

**两个问题的性质**：

1. **`.sb__group` 的语义搞错了**：`--sb-group-head-h: 22px` 是**标题行高**（`tokens.css:243-256` 里的 `--sb-group-head-h 22px`），但早期把它当成了**整组的容器高度**，于是「标题 + 5 个 34px 的项」被压成 22px 高的一行 flex row。这是**把 token 的角色搞混**：token 的名字（`group-head-h`）已经写明了它属于 head，代码却用在了 group 上。
2. **导航区不可滚动** → 三个分组十项超出面板高度时，不是「被挤出可视区」而是**和底部状态卡直接叠在一起**（注释特意强调了「不是被挤下去，是直接压上去」—— 区别在于前者是视觉截断，后者是**两层内容互相覆盖、都读不清**）。

**修复**（同一注释块）：

- `.sb__group` 改列向容器：`display: flex; flex-direction: column; align-items: stretch; height: auto; gap: 2px; margin-top: var(--sb-group-gap); padding: 0`，并**复位早先错写在这一层上的排版属性**（注释 `:1205`「复位早先写在这一层上的排版属性，它们现在归 `.sb__group-head`」）。
- `.sb__nav { flex: 1 1 auto; min-height: 0; overflow-y: auto; overscroll-behavior: contain; scrollbar-width: thin }` —— `min-height: 0` 是 flex 子项能真正滚动的前提（默认 `min-height: auto` 会撑开）。
- `.sb__spacer { min-height: 10px }`（双保险）。
- `.sb--collapsed .sb__nav { flex: 0 0 auto; overflow: visible }`（收起态项目少，不需要滚动）。

**这一轮的教训**：**token 的命名就是它的作用域**。`--sb-group-head-h` 只能给 head 用；把 head 的高度用在 group 上，布局必然错，而且是那种「看起来只是有点挤」的错，只有截图才能发现。

## C.3 第二轮：主区还是一整块不透明矩形，壁纸只剩一条窄缝

**证据**：`glass.css:1231-1256` 的注释块，标题是「主区也做成悬浮面板」。注释原文：

> 「第一轮实机截屏暴露的问题：侧边栏是悬浮玻璃，主区却是一整块不透明的矩形，壁纸只剩侧边栏上方一条窄缝能看见 —— **那不是「悬浮」，那是把窗口刷成了两个世界**。」

（注：注释里写的是「第一轮实机截屏暴露的问题」，但按修复的先后与它引用的状态，它记录的是**改完侧栏之后**那一轮截屏看到的现象 —— 也就是本章按迭代次序归为第二轮的那次。这里保留原文措辞，不替它改口径。）

**问题的性质**：局部做对了（侧栏是悬浮玻璃），但**整体是错的**。壁纸层（`.wp-layer`，`inset: 0`）铺满窗口，可是主区是一整块不透明矩形盖在上面，于是壁纸只在「侧栏上方那条缝」里露出来。用户在视觉上读到的是**两个互不相干的窗口**，而不是「一块玻璃漂浮在同一张壁纸上」。

**修复**：把主区也做成悬浮面板 ——

```css
margin: var(--sb-margin) var(--sb-margin) var(--sb-margin) 0;
border-radius: var(--r-lg);
background: color-mix(in srgb, var(--gl-panel-color) calc(var(--gl-panel-alpha) * 100% + 24%), transparent);
backdrop-filter: blur(var(--gl-panel-blur)) saturate(calc(var(--gl-panel-sat) * 0.7));
box-shadow: var(--gl-sh-panel);
overflow: hidden;
```

并且**复位了一串旧背景**，让主区内部的旧组件不再各自画不透明底：`.titlebar { background: transparent }`、`.plist / .detail / .subbar / .toolbar { background: transparent }`。

**这一轮的教训（值得单独抄出来）**：「悬浮」是一个**整窗口级别的命题**，不是某个组件的属性。只把侧栏做成玻璃、主区留成实心，结果是「更差」而不是「部分达成」—— 因为对比之下，那条窄缝反而让主区的实心更显眼。这一条对任何「局部开始改造」的界面都成立。

## C.4 第三轮：主区被侧边栏压住 —— `margin` 简写把 `margin-left` 也写成了 0

**证据**：`glass.css:1295-1316` 的注释块，标题是「第四轮截屏发现的两个硬伤（都是我第三轮自己改出来的）」。注释原文：

> 「1) **主区被侧边栏压住**：`margin: <t> <r> <b> 0` 这个简写把 `margin-left` 也写成了 0，而侧边栏是 `position: fixed`、不参与流式布局 —— 于是主区从 x=0 开始铺，整列插件名与图标被压在玻璃底下。`margin-left` 必须单独给，且要放在简写之后。」

**根因分析（这是本章最技术的一处）**：

- C.3 的修复写了 `margin: var(--sb-margin) var(--sb-margin) var(--sb-margin) 0` —— 四值简写的第 4 个值是 **`margin-left`**，写 0 的**本意**是「左边不给间距，因为左边原本由流式布局里侧栏的宽度占着」。
- **但这个前提不成立**：侧栏 `.sb` 是 `position: fixed`（`glass.css:74-133`），**它已经脱离了流式布局**，不再占据主区左边那 264px。
- 于是主区从 `x = 0` 开始横向铺满 → 插件名与图标整列被压在玻璃面板底下。

**修复**：**在 margin 简写之后单独再给一次 `margin-left`** ——

```css
margin-left: calc(var(--sb-w-expanded) + var(--sb-margin) * 2);
```

注释特意加了一句「margin-left 必须单独给，**且要放在简写之后**」—— 因为 CSS 简写会覆盖它之前的同属性声明，顺序错了等于没写。`.shell-main--collapsed` 同样补了 `margin-left`（换 `--sb-w-collapsed`）。

**这一轮的教训**：**一旦某个元素改成 `position: fixed`，所有「它原来占位」的假设全部作废**。而且失效方式很隐蔽 —— 布局不报错、不塌陷，只是内容被另一层盖住，只有截图能看出来。

## C.5 第四轮：主区透明度的账从「面板」改记到「衬底」

**证据**：同一个注释块的 2)。注释原文：

> 「2) **数据落在太透的衬底上**：主区原来用 `--gl-panel-color(0.52+24%)` 叠粉壁纸后描述文字发灰 —— §0 第一条硬规则就是『数据永不落在模糊层上』，所以主区改用更实的 `--gl-bed-color`，**透明度的账记在衬底上而不是面板上**。」

**修复**：

```css
background: color-mix(in srgb, var(--gl-bed-color) calc(var(--gl-bed-alpha) * 100% + 14%), transparent);
backdrop-filter: blur(calc(var(--gl-panel-blur) * 0.6)) saturate(calc(var(--gl-panel-sat) * 0.5));
```

**为什么这是「账记在衬底上」**：

- 改之前：主区用**面板色**（`--gl-panel-color #0c0e16` @ 0.52 + 24% = 0.76），blur 用满（30px）、saturate 用 0.7 倍。
- 改之后：主区用**衬底色**（`--gl-bed-color #12151c` @ 0.72 + 14% = 0.86），blur 降到 0.6 倍（18px）、saturate 降到 0.5 倍（0.725）。
- 两组数值的差别不只是「更不透明」，而是**语义换了层**：面板层是「玻璃」，衬底层是「玻璃柜里的台面」。主区承载的是插件名、版本号、描述文字 —— 按 design-v3 §0 第一条硬规则（`:25-29`）和 §1.6 第 ① 条（`:321-328`「数字是硬的：≥0.72 alpha 衬底，数字与版本 ≥7:1」），**数据必须落在衬底上**。
- 同时把 blur 与 saturate 都减半，是兑现 §0 第二条硬规则「**模糊预算是分配的不是铺开的**」：主区面积最大，如果把模糊预算全铺在主区上，不仅性能吃不住（§2.7 同屏 `backdrop-filter` ≤2），壁纸也会被糊得没有存在感（§0 第三条「壁纸永远比内容弱一档」，但「弱」不等于「消失」）。

**这一轮串起了 §0 的三条硬规则**：第四轮这一改，同时命中了 ①数据落在衬底上 ②模糊是分配的 ③壁纸要留一档可见度。所以这一轮之后外壳才算「做对」。

## C.6 噪声值的校准落地

`--gl-noise` 是 §6.7 那 14 项里**唯二真正被 ref-notes 改了值**的（另一项是浅色同一个 token）：

| token | design-v3 §6.7 的值 | 实现最终值 | 依据 |
|---|---|---|---|
| `--gl-noise`（深） | 0.024 | **0.02** | ref-notes §1.28 一手源码 `sc_noiseOpacity = 0.02f`（2%） |
| `--gl-noise`（浅） | 0.016 | **0.014** | 同上；浅色取 0.02 的 0.7 倍 |
