# DSH 插件台 —— 设计简报（第二阶段用）

> 这份文件是 `/motion-web` + `/frontend-design` 两个技能对本项目的约束蒸馏。
> 第一版（功能版）不套用这里的审美要求，只保证状态完整；**第二阶段按这份执行**。

---

## 0. Brief

**主题**：一个本地开发者工具，管理一台机器上 DSH 各个 profile 的插件。
**受众**：一个人 —— 这台机器的使用者。他每天看它两三次，每次待 30 秒到 2 分钟。
**页面首要任务**：让「我的插件现在是什么状态、有哪些能更新、刚才那个操作到底改了什么」在**第一屏**就成立。

关键含义：这不是一个营销页。它的 hero 不是标题，是**数据本身**。它的「记忆点」不应该是装饰，
而应该是一个只有这个工具才有的东西 —— 候选：

- 一次操作前后 `bundles` 数组的**逐位差异**（哪个包在哪个下标被插入/移出）——这是本工具的
  核心语义，也是最容易做砸的地方。做成一个可读的、有动画的序列视图。
- 「装了什么」vs「加载了什么」这对张力：同一个包在 `dependencies` 和 `bundles` 里存在与否
  有四种组合，四种组合就是四种状态。任何列表都必须把这两个维度画出来。
- GitHub 输入的实时预检：从一串 URL 到「这是 owner/repo，ref=main，pnpm spec = github:owner/repo」
  的逐步揭示。

**禁止**：仪表盘式的假图表、无意义的统计数字、为了填满首屏的装饰性渐变。

## 1. 从 frontend-design 技能继承的硬约束

### 必须避开（这些是 AI 生成设计的破绽）

- 只给标题里的一个词加斜体 / 加粗 / 变色。
- 标签全部大写（`ALL CAPS` + 字距）当装饰。
- 在内容上方加不必要的 eyebrow 小标签。
- 结构装置（描边 / 边框 / 编号 / eyebrow / 分隔线 / 标签）**必须编码有用信息**。编号只在内容真的是序列时使用。
- 每个 section 都 fade-and-slide-up；每张卡都 hover 抬升 —— 这两个是通用默认，禁止。
- 非用户触发的动效要克制：一次编排好的载入序列 > 零散效果。

### 五类聚集特征（明确避开）

1. 暖奶油底 `#F4F1EA` + 高对比衬线 + 陶土色 `#D97757`
2. 近黑底 + 单一亮酸绿或朱红强调
3. 报纸式栏线、零圆角、密集栏
4. SaaS 卡片套件：内容切成同尺寸圆角卡、全站一个圆角、同一个柔和灰阴影、渐变当装饰
5. 跟主题无关的模板外壳：每个标题上方全大写字距标签；用「·」连接元字符串；
   `WORD — 片段` 式标签；用 `#0B0B0B`/`#111` 冒充黑；小数据标签用等宽字体；
   链接/按钮文本后缀「→」

### 字体

- 一到两套，**明显区分**，明确字重 / 字宽 / 字距。
- 遵循 The Elements of Typographic Style 的字号阶梯。
- 正文行长 < 80 字符。

### 流程（顺序不能乱）

1. 先出**紧凑 token 系统**：4–6 个命名 hex 的核心色板 + 字体及角色 + 版式概念（含 ASCII 线框与对齐方式）+ 高层原则。
2. 拿这套 token 对照简报复核：**任何读起来像「换成同类页面也会这么做的通用默认」的部分都要改掉**，
   并说明改了什么、为什么。
3. 然后才写代码。

### 克制

- 大胆只用在一处，一处记忆点，周围保持安静。
- 不给装饰。
- 默默达到质量底线：响应式到窗口最小尺寸、可见键盘焦点、尊重 reduced-motion、视觉可达、配色和谐。
- 边做边截图自评。
- 写 CSS 注意**选择器特异性互相抵消**（尤其 type 选择器如 `.section` 与元素选择器如 `.cta`，
  常见于 section 之间的 padding/margin）。

### 文案即设计内容

- 从最终用户视角命名，用简单语言说明「是什么 / 做什么」。
- 默认主动语态。
- CTA 说清点了会发生什么（「更新 3 个插件」而不是「提交」）。
- 同一动作在整个流程中保持同名（按钮「停用」→ 结果提示「已停用」）。
- 错误不道歉、不含糊：说明发生了什么与怎么修。
- 空状态是行动邀请。
- 句首大写、无填充词、每个元素只干一件事。

## 2. 从 motion-web 技能继承的硬约束

### 优先级排序

1. **动效概念与编排 = 页面设计（并列第一）**
2. 页面作为成品：section + 真实文案、组件词汇表与状态矩阵、token 层、非 happy-path 状态
3. 轻量 3D
4. 性能 / 无障碍 / reduced-motion

### 硬规则

- **静帧半成品 = 失败**。评审必须**关掉动效截图**看静帧。
- 禁止默认模板感：默认 hero、三栏特性卡、紫色渐变、统一 hover 抬升、全页 fade-up、
  装饰代替设计、首屏烧光预算。

### Build Order

0. 选页面栈档位（本项目已定：Electron + Vite + React，不要再动）
0.5 选动效栈档位
1. 选 blueprint + **写真实文案**（不是 lorem）
2. 设计页面：macrostructure / 字号阶梯 / 配色 / 间距节奏
2.5 铺 token 层与 scales：三级 token、`clamp()` 流式字号、字体 metric override、`@layer` 顺序
3. 选动效 token：时长 / 缓动 / spring
3.5 建**组件词汇表与完整状态矩阵**：hover / `:focus-visible` / active / disabled / loading / error / empty / success
4. 查 pattern-recipes.md
5. 图片资产先过资产管线
6. 实现；探针（`__seek` / `__hold` / 可钉时钟）边做边建
7. 多轨滚动时间轴横向铺开
8. 非按钮交互标注可发现性
9. 先跑设计闸门，再跑动效闸门
10. production-polish 收尾：head / OG / favicon / 404 / 空态 / 暗色模式 / §9 十项人工检查
11. 验证桌面 + 移动 + reduced-motion + 可发现性

### 关键原则

- 跟随类（相机 / 光标 / 轨道 / 提示）**不是 spring 问题**，稳态滞后是 `speed / k`。
- 「飘」是静帧比例问题，不是缓动曲线问题。
- **一个组件没有全部状态就不算建成。**
- 写代码前必须先读 build-mode.md 对应框架章节与 Failure Patterns 表。

### 输出契约（full-build 时必须报告）

- 所选 blueprint 及理由
- 页面栈档位
- 组件方言（creative vs product）
- 动效概念
- **每一个被发明的真实信息槽位（显式列出）**
- production-polish §9 的结果

## 3. 本项目的特殊约束

「组件方言」应当选 **product**，不是 creative —— 这是每天用的工具，不是作品集。
但 **product 不等于平庸**：本工具的记忆点应该是「状态差异的可见化」，而不是装饰。

要设计的关键组件（每个都必须有完整状态矩阵）：

| 组件 | 难点 |
|---|---|
| 插件行 | 四个维度叠加：装/未装 × 加载/未加载 × 可更新/最新 × 官方/第三方 |
| 差异视图 | 一次操作后 `bundles` 数组的逐位变化，要能一眼看出插在哪、删了哪个 |
| GitHub 输入预检 | 从原始输入到 pnpm spec 的逐步揭示，失败时要说清是哪一步失败 |
| 日志抽屉 | 流式、可取消、`\r` 进度行、失败摘要 |
| 环境探测结果 | 找不到东西时是说清楚哪一条找不到，而不是一个红色叹号 |

**明暗两套都要做**（`theme: 'dark' | 'light' | 'system'` 已经在契约里）。

## 4. 追加需求带来的新界面（Master 第 2 轮，7 条）

功能版已经把这些做出来了（朴素实现），**设计阶段要重新设计它们的呈现**：

| 新界面 | 现在的样子 | 设计要解决的问题 |
|---|---|---|
| 插件图标槽 | 行左侧 20px 方块；详情顶部 56px | **大部分插件没有图标**，占位（monogram）必须体面到能当正常状态看，不能像「加载失败」。有图 / 无图两行并排时视觉重量要接近，否则列表会像坏了一半 |
| 代理设置 + 测延迟 | 输入框 + 「测试」按钮 + 一行结果 | 「通了 · 38 ms」这个数字是本工具**唯一一个实时测量值**。它该被设计成一个有份量的读数，而不是灰色小字。失败态要说清是哪一层失败（连不上 / CONNECT 被拒 / 超时） |
| DSH 进程状态 + 启停 | 侧栏底部一个点 + 两句话 + 两个按钮 | 这是全局状态，不是某个 profile 的属性。它现在的摆放位置（侧栏底部）和「过滤」并列，层级是错的 |
| 执行前确认弹窗 | 标准居中卡片 | 确认内容必须**具体到能判断**（来源 spec / 装到哪个 profile / 会改哪两个文件 / from→to）。这是本工具「可审计」性格的最强体现点 —— 值得给它一个专属版式，而不是通用 modal |
| 导入清单 | 第 4 个 tab + 预览卡 | 「清单里有 N 个 / 已有 M 个 / 要装 K 个」是一个集合差运算。三个数字的关系应该被**画出来**（三段式进度条 / 两个集合的对照），而不是三行文字 |
| 系统托盘菜单 | 原生 Windows 托盘菜单 | 原生控件，设计空间有限。**能设计的只有图标本身**：16px 下那个 1024px 的插画会糊成一团，需要判断是不是该做一版**专供托盘的简化图形** |
| 标题栏 logo | 20px 图 + 应用名 | 无边框窗口的自绘标题栏。logo 在这里是「品牌唯一出现的位置」，不要让它在别处重复 |

**新增的状态矩阵要求**：

- 插件图标：有图 / 无图 / 加载中 / 加载失败 → 四态，且**四态的宽度必须一致**（列表不能因为图标状态而跳动）
- DSH 进程：运行中 / 未运行 / 正在启动 / 正在退出 / 探测失败 → 五态。前两态要有区分度但不能刺眼（不是红绿交通灯）
- 代理测速：未测 / 测中 / 通 / 失败 → 四态，结果必须**跟输入绑定**（改了输入就作废）
- 确认弹窗：危险（卸载 / 退出 DSH）/ 普通（安装）/ 批量（更新全部，要求手打确认词）→ 三档，档与档之间要有可见差异
- 清单导入：空文件 / 解析失败 / 全部已装（空态）/ 有缺的（正常）/ 安装中 / 部分失败 → 六态

**一个新出现的排版风险**：确认弹窗与预览卡都要列「最多 12 条 + …等 N 个」。**这个截断规则要在设计里统一**（同一个产品里不要一处写「…等 3 个」另一处写「还有 3 个」）。
